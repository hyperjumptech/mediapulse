## Purpose

**hermes-worker** is a long-running Node/Bun app that runs the DataQueue **processor** and **supervisor** for the Hermes scheduler. It ensures the cron job `hermes-check-schedules` exists, processes `check_schedules` jobs (poll due schedules, execute them via `@workspace/hermes-scheduler`), and runs the supervisor (stuck-job reclaim, cleanup). Hermes (Next.js) no longer runs the queue and can be deployed without a long-running server; run hermes-worker on a persistent host for scheduled pipeline runs.

## Features

- **Queue init** — Connects to DataQueue using `PG_DATAQUEUE_DATABASE`.
- **Cron registration** — Ensures `hermes-check-schedules` (every minute) exists.
- **Processor** — Runs job handlers (e.g. `check_schedules`: get due schedules, execute each via hermes-scheduler).
- **Supervisor** — Reclaims stuck jobs, cleans old jobs/events.
- **Agent token client** — When `AGENT_AUTH_API_URL` and `AGENT_API_KEY` are set, the worker fetches **short-lived JWTs** from `POST /api/token` (using the API key as credential) and uses those tokens when invoking agents, instead of sending the raw key. Use an API key with **purpose `scheduler`** so token issuance is allowed. Revoking that key in the admin UI stops the worker from obtaining new tokens after expiry.
- **HTTPS enforcement** — When `REQUIRE_HTTPS_AGENT_ENDPOINTS=true`, agent endpoint URLs must use HTTPS (or `http://localhost` / `http://127.0.0.1` for local dev).
- **Graceful shutdown** — SIGTERM/SIGINT drain processor and supervisor, then exit.

## Scripts

- `pnpm dev` — Start with hot reload (Bun). Uses `.env.local` in the app root (loaded via `dotenv -e ./.env.local`).
- `pnpm build` / `pnpm start` — Build and run production build.
- `pnpm run migrate-dataqueue` — Run DataQueue schema migrations.
- `pnpm run migrate-dataqueue:dev` — Migrate with dev env and verbose output.

From repo root: `pnpm dev:hermes-worker`.

### Setup DataQueue schema

Hermes-worker uses the **DataQueue** tables (e.g. `job_queue`, `cron_schedules`) in the `dataqueue` schema. Before running the worker for the first time (or after pointing it at a fresh database), run the migrations from this app:

```bash
cd apps/hermes-worker
pnpm migrate-dataqueue:dev
```

If you see an error like `relation "cron_schedules" does not exist` when starting hermes-worker, it means the DataQueue migrations have not been applied yet—run the command above against the target database.

## Environment

- **PG_DATAQUEUE_DATABASE** (required) — DataQueue DB connection (e.g. same as `DATABASE_URL` with `?schema=dataqueue`).
- **DATABASE_URL** — Used by Prisma in job handlers (schedule execution).
- **AGENT_API_KEY** — Credential for agent invocation. When **AGENT_AUTH_API_URL** is also set, this key is used only to call `POST /api/token`; the worker then sends the returned short-lived JWT to agents. Use a key with purpose `scheduler` (create via API key CRUD with `purpose: "scheduler"`).
- **AGENT_AUTH_API_URL** (optional) — Base URL of agent-auth-api. When set with `AGENT_API_KEY`, the worker uses the token client (short-lived JWTs) instead of the raw key when invoking agents.
- **REQUIRE_HTTPS_AGENT_ENDPOINTS** (optional) — Set to `true` in production to reject agent endpoints that use `http` with a non-local host. Localhost and 127.0.0.1 are always allowed.

## Workspace dependencies

- `@workspace/hermes-scheduler` — Due schedules, execution, next-run logic.
- `@workspace/database` — Prisma client for schedules and execution.
- `@workspace/env`, `@workspace/logger`, `@nicnocquee/dataqueue`, `got`.
