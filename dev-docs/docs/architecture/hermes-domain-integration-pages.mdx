The Hermes dashboard (`apps/hermes/dashboard`) does **not** query Mediapulse (or other product) databases for these screens. Instead, each **domain integration** registers a **dashboard manifest** with Hermes (see [Dashboard manifest](#dashboard-manifest)). The Next.js app loads that JSON from the orchestration database, renders sidebar links and App Router pages, and **proxies** HTTP to the integration’s `baseUrl` using the UI template and API contract declared for each page. Today that template is **`table-v1`**—a specification for how a domain resource plugs into the Hermes dashboard UI and HTTP surface; see [What is the table-v1 template](#what-is-the-table-v1-template).

For the split between Hermes and Mediapulse apps, see [Hermes and Mediapulse domains](/architecture/domains). For the Mediapulse service that implements the HTTP handlers, see [Domain API](/mediapulse/apps/domain-api). For the shared Zod schemas and client types, see [hermes-domain-contract](/hermes/packages/hermes-domain-contract).

## Dashboard manifest

The **dashboard manifest** is the structured JSON payload (`dashboardManifestSchema` in `@hermes/domain-contract`) that a domain integration sends when it registers with Hermes (`dashboard` field on `registerDomainIntegrationRequestSchema`). Hermes persists it on the **orchestration** `DomainIntegration` row as **`dashboardManifest`** so the dashboard can be rebuilt without re-calling the domain service.

**What it is for:** It tells Hermes **which screens** to show for that integration (sidebar entries, labels, ordering), **which URL paths** under `/dashboard/{integrationKey}/…` map to which resource, and **which UI template** (`template` on each page) applies so Hermes knows how to render the page and which outbound HTTP calls to make.

**What is inside:** The manifest has two top-level fields:

| Field             | Role                                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `templateVersion` | Version of the manifest document shape (currently only `1`). Bumps here if the list of allowed fields or semantics change. |
| `pages`           | Array of **dashboard pages** (`dashboardPageSchema`), one per sidebar entry / resource.                                    |

Each **page** describes one integrated resource. Important fields include:

| Field                                           | Role                                                                                                                                                       |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                            | Stable id for the page within the manifest.                                                                                                                |
| `label`, `description`, `icon`, `order`         | Sidebar and UI copy; `order` controls sort order in the nav.                                                                                               |
| `pathSegment`                                   | Second segment after `/dashboard/{integrationKey}/` (e.g. `tickers` → `/dashboard/mediapulse/tickers`).                                                    |
| `template`                                      | Which **dashboard UI specification** to use. Currently only **`table-v1`** is allowed (`dashboardTemplateSchema`; more values may be added later).         |
| `apiPrefix`                                     | Path prefix on the domain’s `baseUrl` for this resource’s HTTP API (Hermes concatenates `baseUrl` + `apiPrefix` for meta, list, CRUD, and custom actions). |
| `columns`, `searchableFields`, `sortableFields` | List/table configuration (columns also carry types such as `text` or `date-time`).                                                                         |
| `actions`                                       | Whether create, update, and delete are supported for this resource.                                                                                        |
| `createSchema` / `updateSchema`                 | Optional JSON Schema fragments for Hermes create/update forms (subset parsed by the dashboard).                                                            |
| `customActions`                                 | Optional extra actions (e.g. file upload) with `method`, `path` suffix under `apiPrefix`, and `ui` hint.                                                   |
| `createNavigation`                              | `modal` vs `full-page` create/edit flows.                                                                                                                  |
| `preview`                                       | Optional preview control tied to a form field when the integration registers the `preview-expansion` capability.                                           |

At runtime, Hermes merges manifest data with live **meta** responses from the domain where needed (e.g. echoed columns and schemas) so the UI stays consistent with the server.

## What is the table-v1 template

**table-v1** is the **first** (and currently **only**) **dashboard UI specification template** in `@hermes/domain-contract`: it defines how a **domain-owned resource** is integrated into the Hermes dashboard **in terms of** navigation, page layout (table list, modals vs full-page editors), and the **HTTP surface** the domain must implement so Hermes can load metadata, paginated lists, and optional CRUD. The `-v1` suffix versions that contract so a future **`table-v2`** or an unrelated template (e.g. a non-table layout) can be added without silently changing existing integrations.

Concretely, “table-v1” refers to:

1. **Manifest flag** — Each page in `dashboard.pages` sets `template: "table-v1"`. That selects this specification. Additional `template` values may be introduced later for different UI patterns.

2. **HTTP API + Zod shapes** — For pages that use this template, the domain exposes the endpoints under the page’s `apiPrefix` (meta, list query, optional CRUD) documented in [Table-v1 HTTP calls](#table-v1-http-calls). Hermes validates responses with `tableV1MetaResponseSchema`, `tableV1ListResponseSchema`, and related types in the same package. In conversation, “table-v1” usually means this full bundle: **manifest choice + routes + validators**.

Other templates (if added) would ship their own manifest `template` value, UI entry points, and HTTP/Zod contracts; the **dashboard manifest** remains the single registration blob that lists which template each page uses.

## Registration and storage

1. A domain service (for example Mediapulse **domain-api**) calls Hermes `POST /api/domain-integrations/register` with a body that matches `registerDomainIntegrationRequestSchema` (key, name, `baseUrl`, optional capabilities, and a `dashboard` field containing the [dashboard manifest](#dashboard-manifest)).
2. Hermes persists the row in the **orchestration** database (`DomainIntegration`), including `dashboardManifest` JSON.
3. `apps/hermes/dashboard/lib/domain-integrations.ts` exposes `getActiveDomainIntegrations`, `getDomainIntegrationByKey`, and related helpers so the UI can resolve `baseUrl` and `dashboard.pages` at runtime.

<Mermaid
  chart={`flowchart LR
  DomainSvc["Domain service"] -->|"POST /api/domain-integrations/register"| HermesAPI["Hermes API"]
  HermesAPI --> OrchDB[("Orchestration DB")]
  OrchDB --> Helpers["Dashboard helpers"]
  Helpers --> DashUI["Hermes dashboard"]
`}
/>

If registration fails or the DB is empty, the sidebar simply omits domain sections; individual routes return errors or `notFound()` when the key or resource is unknown.

## Sidebar and layout

`apps/hermes/dashboard/app/dashboard/layout.tsx` loads active integrations and passes them into `DashboardShell` → `AppSidebar`.

For each integration, the sidebar renders one link per manifest page:

- **URL pattern:** `/dashboard/{integrationKey}/{pathSegment}`
- **Labels** come from each page’s `label` in the manifest (`DashboardPage` in `@hermes/domain-contract`).

The **second** path segment after `/dashboard/` must match a page’s `pathSegment` for that integration. Hermes core routes (pipelines, agents, …) live outside this pattern, so they do not collide as long as integration keys and `pathSegment` values are chosen carefully.

## App Router entry points

| Route                                                | Role                                                                 |
| ---------------------------------------------------- | -------------------------------------------------------------------- |
| `[integrationKey]/[resource]/page.tsx`               | Default **table-v1** list view; delegates to `DomainTablePage`.      |
| `[integrationKey]/[resource]/new/page.tsx`           | **Full-page create** when meta says `createNavigation: "full-page"`. |
| `[integrationKey]/[resource]/[itemId]/edit/page.tsx` | **Full-page edit** for the same navigation mode.                     |

All of these are wrapped with `withAuthProtection` so only authenticated dashboard users can open them.

## Resolving the integration and `apiPrefix`

`apps/hermes/dashboard/lib/domain-dashboard.ts` is the central place for server-side calls:

1. **`getDashboardPage`** (internal) loads the integration with `getDomainIntegrationByKey(integrationKey)` and finds the manifest entry where `pathSegment === resource`.
2. It returns `{ baseUrl, page }` where `page.apiPrefix` is the domain-owned HTTP prefix for that resource (for example a path under `/v1/hermes-dashboard/...` on domain-api).

If the integration is inactive, missing, or the resource is not in the manifest, the helpers throw; the page layer surfaces that as a failed request or error UI.

## Table-v1 HTTP calls

For each table-v1 page, Hermes typically issues:

| Operation                                                 | Method | URL shape                                                  |
| --------------------------------------------------------- | ------ | ---------------------------------------------------------- |
| Metadata (columns, actions, form schemas, custom actions) | GET    | `{baseUrl}{apiPrefix}/meta`                                |
| Paginated list                                            | GET    | `{baseUrl}{apiPrefix}?page=&pageSize=&q=&sortBy=&sortDir=` |
| Create                                                    | POST   | `{baseUrl}{apiPrefix}`                                     |
| Read one (full-page edit)                                 | GET    | `{baseUrl}{apiPrefix}/{id}`                                |
| Update                                                    | PATCH  | `{baseUrl}{apiPrefix}/{id}`                                |
| Delete                                                    | DELETE | `{baseUrl}{apiPrefix}/{id}`                                |

Responses are validated with `tableV1MetaResponseSchema`, `tableV1ListResponseSchema`, etc., from `@hermes/domain-contract`.

<Mermaid

Requests send `Content-Type: application/json`. Hermes adds `Authorization: Bearer <JWT>` (minted via agent-auth-api **`POST /api/token`** using that integration’s **decrypted API key**, with **`HERMES_INTERNAL_API_KEY`** used to unwrap ciphertext at rest) when agent auth is configured so the domain API can verify the caller (**`POST /api/verify`**).

## Rendering the list page (`DomainTablePage`)

`apps/hermes/dashboard/app/dashboard/domain-table-page.tsx` is a **server component** that:

1. Parses search params (pagination, search, sort).
2. Loads **meta** and **list** in parallel via `getDomainTableMeta` and `getDomainTableList`.
3. Builds create/update forms from `meta.createSchema` / `meta.updateSchema` (JSON Schema subset parsed by `parseDomainTableFormFieldsFromJsonSchema`).
4. Defines **server actions** that call `createDomainTableItem`, `updateDomainTableItem`, `deleteDomainTableItem`, then `revalidatePath` and redirect as needed.

<Mermaid
  chart={`flowchart TD
  Params["Parse search params"] --> Parallel["Parallel server fetch"]
  Parallel --> Meta["getDomainTableMeta"]
  Parallel --> List["getDomainTableList"]
  Meta --> Render["DomainTablePage"]
  List --> Render
  Render --> Forms["Forms from meta schemas"]
  Render --> Actions["Server actions CRUD"]
  Actions --> Reval["revalidatePath and redirects"]
`}
/>

**Modal vs full-page create:** If the manifest (and echoed meta) sets `createNavigation` to `"modal"`, create/update UI is inline on the list page. If it is `"full-page"`, the list page links to `/new` and row actions link to `/{itemId}/edit`, which use `DomainTableFullPageEditor` instead.

**Custom actions:** When meta includes `customActions` with `ui: "json-file-upload"`, Hermes renders the upload card and POSTs to `{baseUrl}{apiPrefix}{action.path}` via `invokeDomainTableCustomAction`.

**Preview:** If meta includes `preview` and the integration’s capabilities include `preview-expansion`, the UI can call the preview flow (`previewDomainExpansion` uses `createDomainIntegrationClient`, not the raw table-v1 meta/list fetch).

## Related flows outside these pages

- **Step-input expansion** and **preview** in pipelines use the same registered integration and `@hermes/domain-contract` client; see [Data source expansion](/guide/data-source-expansion).
- **Pipeline run ticker pickers** resolve the registered **mediapulse** integration (manifest + `baseUrl` from orchestration) to list tickers through the same table-v1 list endpoint pattern (`fetchAllTickersForPipelineRun` in `domain-dashboard.ts`).

## Implementing a new table on the domain side

1. Add HTTP handlers on the domain service for `GET …/meta`, `GET …` (list), and optional CRUD routes under your chosen `apiPrefix`.
2. Add a `dashboard.pages[]` entry (template `table-v1`, `pathSegment`, `apiPrefix`, columns, actions, schemas, etc.) to the payload you send on registration.
3. Configure **JWT** verification on the domain service (`AGENT_AUTH_API_URL` → **`POST /api/verify`**) when the API is protected.

The exact field list and validation rules live in `dashboardPageSchema` / `dashboardManifestSchema` in `packages/hermes/domain-contract/src/contracts.ts`.
