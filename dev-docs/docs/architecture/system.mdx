## System overview

**Hermes** (Next.js) is the dashboard and API for pipelines, tickers, agents, and schedules. The **hermes-worker** app is a long-running process that runs the scheduler (DataQueue processor and supervisor): it polls for due schedules and executes pipeline steps by invoking agents over HTTP. This split lets Hermes stay stateless (no long-running server); run hermes-worker on a persistent host for scheduled runs. Agents call the **agent-data-api** for reading/writing pipeline data and the **agent-auth-api** for token verification. The **agent-registry-api** is used to register agents. All persistent data lives in PostgreSQL via the shared **database** package.

The agent set now includes `query-analysis`, `data-collection`, `analysis`, `content-generation`, and `delivery`.

## Flow

1. **Hermes** (Next.js) serves the dashboard and schedule/pipeline CRUD. It does not run the queue or cron; use **hermes-worker** for that.
2. **hermes-worker** runs the DataQueue processor and supervisor: a cron job enqueues `check_schedules` every minute; the worker polls due schedules and runs pipeline steps (query-analysis → data-collection → analysis → content-generation → delivery), sending `POST` requests with params and `Authorization: Bearer <apiKey>` to each agent.
3. **Agents** validate the body, verify the token via **agent-auth-api**, run their logic, and call **agent-data-api** to read/write ticker/newsletter/subscriber data.
4. **agent-registry-api** stores agent metadata; Hermes (or tooling) can register agents there.
5. **PostgreSQL** holds users, API keys, tickers, pipelines, agents, schedules, and all pipeline-produced data. DataQueue uses the same DB with a separate schema (`dataqueue`); run migrations from hermes-worker: `pnpm --filter hermes-worker run migrate-dataqueue`.
