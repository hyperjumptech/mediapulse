This page explains **how the parts of the system talk to each other**: who calls whom, which credentials are on the wire, and how verification works.

**See also:** [System overview](/architecture/system) for a diagram, [Hermes and Mediapulse domains](/architecture/domains) for boundaries, [Production](/production) for environment variables.

## Auth mechanisms (overview)

| Flow                                               | Credential on the wire                                                                                                                                        | Verified by                                                           |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Minting** (Hermes / worker → agent-auth-api)     | Preset **`HERMES_INTERNAL_API_KEY`** or decrypted **domain integration** API key in `Authorization: Bearer …` on **`POST /api/token`** (depends on call site) | Preset vs DB hash + ciphertext (see agent-auth-api)                   |
| **Minting** (Mediapulse / agents → agent-auth-api) | **`DOMAIN_INTEGRATION_API_KEY`** (same secret Hermes created for that integration) on **`POST /api/token`**                                                   | Key lookup in DB (purpose `domain_integration` or legacy `scheduler`) |
| **Invocation** (Hermes / worker → agent)           | Short-lived **JWT**                                                                                                                                           | Agent calls `POST /api/verify`                                        |
| **Agent → agent-data-api / agent-registry-api**    | **Same JWT** the agent received for the run (forwarded), or a **new JWT** minted with the **domain_integration** key (e.g. startup registration)              | Each API uses `POST /api/verify` via `@workspace/agent-auth-client`   |
| **Dashboard / admin** (when applicable)            | Raw API key on some routes                                                                                                                                    | `POST /api/verify-api-key`                                            |

Invocation proves the caller is allowed to run the step. **agent-data-api** and **agent-registry-api** do not accept raw API keys from agents for normal requests—they expect a **JWT** and verify it the same way agents do.

## Invocation flow: Hermes or hermes-worker → Agent

When a pipeline runs (from the dashboard or on a schedule), the caller **never** sends long-lived secrets to agents. Hermes dashboard and hermes-worker mint JWTs via `POST /api/token` using the **decrypted domain integration API key** for that pipeline’s integration (or the internal preset where the flow is Hermes-only). They send the returned **JWT** to agents.

**Domain and agents:** To mint JWTs for **Mediapulse ↔ Hermes** or **registry auto-register**, an admin creates a **domain integration** in Hermes (integration key + one-time API key) and sets **`DOMAIN_INTEGRATION_API_KEY`** and **`DOMAIN_INTEGRATION_KEY`** in Mediapulse/agent env.

**Steps:**

1. **Hermes** (manual run) or **hermes-worker** (scheduled run) loads the **domain integration** credential for the pipeline (or uses **`HERMES_INTERNAL_API_KEY`** where applicable) and calls **agent-auth-api** `POST /api/token` with `Authorization: Bearer <secret>`.
2. **agent-auth-api** matches the bearer token to the preset or a **domain_integration** key hash, signs a JWT with `AGENT_AUTH_JWT_SECRET`, and returns `{ token, expiresIn }` (e.g. 15 minutes).
3. Hermes/hermes-worker **caches** the JWT and uses it for all agent requests until close to expiry, then fetches a new one.
4. For each pipeline step, the caller sends `POST` to the agent URL with `Authorization: Bearer <jwt>` and the step input/config.
5. The **agent** (via `@workspace/agent-runtime` bearer middleware) receives the request, extracts the Bearer token, and calls **agent-auth-api** `POST /api/verify` with that token.
6. **agent-auth-api** `POST /api/verify` is **JWT-only**: it verifies signature and expiry. If the token is not a JWT or is invalid, it returns 401. The agent rejects the request unless it gets 200.
7. The agent runs its logic and returns the result.

**Important:** The internal preset key is only ever sent to agent-auth-api. Agents only ever see the JWT, so a leaked JWT expires in minutes. Rotate **`HERMES_INTERNAL_API_KEY`** at deploy time if it is compromised.

## Agent → agent-data-api / agent-registry-api (JWT)

Agents call **agent-data-api** (read/write pipeline data) and optionally **agent-registry-api** (register). Both services use **bearer JWT** auth: the same **`Authorization: Bearer <jwt>`** the agent received for the pipeline step is forwarded to agent-data-api via `@workspace/agent-data-api-client`. For **registry** at startup (outside a pipeline), the agent typically mints a JWT using **`DOMAIN_INTEGRATION_API_KEY`** (dashboard key, purpose **`domain_integration`**) and `POST /api/token`, then calls register with that JWT.

**Steps:**

1. During a pipeline run, the agent forwards the **invocation JWT** to **agent-data-api** (SDK passes the token from the request context).
2. **agent-data-api** and **agent-registry-api** call **agent-auth-api** `POST /api/verify` with the Bearer token (via `verifyTokenViaAuthApi`).
3. **agent-auth-api** verifies the JWT signature and expiry. On success, the data or registry handler runs.

JWT verification is centralized in **agent-auth-api**; data and registry APIs do not store keys for agent traffic.

- **Invocation:** Hermes/hermes-worker → `POST /api/token` with **`HERMES_INTERNAL_API_KEY`** → JWT → agent → `POST /api/verify`. Internal preset never goes to the agent.

- **verify-api-key:** Used for flows that present a **raw API key** (e.g. some dashboard operations), not for normal agent→data-api traffic.

## Where to configure what

| Component          | Needs                                                                                | Used for                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| **agent-auth-api** | `AGENT_AUTH_JWT_SECRET`, `HERMES_INTERNAL_API_KEY`                                   | Signing/verifying JWTs; validating preset bearer for Hermes minting.                           |
| **Hermes**         | `AGENT_AUTH_API_URL`, `HERMES_INTERNAL_API_KEY`                                      | Minting JWT when user runs a pipeline from the dashboard (same preset as worker and auth API). |
| **hermes-worker**  | `AGENT_AUTH_API_URL`, `HERMES_INTERNAL_API_KEY`                                      | Minting JWT for scheduled pipeline runs.                                                       |
| **Agent**          | `AGENT_AUTH_API_URL`                                                                 | Verifying invocation JWT via `POST /api/verify`.                                               |
| **Agent**          | Forwarded **JWT** (and optional **domain_integration** `DOMAIN_INTEGRATION_API_KEY`) | Data/registry: same JWT as invocation, or mint via `POST /api/token` for startup registration. |

For a full list of env vars per app, see [Production](/production).
