## Purpose

**`@hermes/dashboard`** is the orchestration UI: **pipelines** (sequences of agents), **agents**, **agent configs**, **variables**, **domain integrations** (per-integration API keys and lifecycle), **schedules**, and **HTTP triggers**. This Next.js app exposes the dashboard and APIs for creating and editing schedules and triggers. The **scheduler** itself (DataQueue processor and supervisor) runs in **`hermes-worker`** so the dashboard stays a normal web app without owning the queue process.

## Quick overview

- **Agents** are executable units and can have multiple versions. An agent can register itself when it starts up (via agent-registry-api).
- **Pipelines** are created by admins as an ordered series of agent steps. Admins configure the input and config for each step.
- **Schedules** define when a pipeline should run; **HTTP triggers** expose an authenticated URL to run a pipeline on demand.

## Features

- **Dashboard UI** — Manage pipelines, pipeline steps, agents, domain integrations, and schedules. Domain-owned resources are rendered from a registered dashboard manifest (`table-v1`) rather than hardcoded Prisma-backed pages in this app.
- **Domain pages from integration manifest** — Each domain integration registers an **integration id** (stable string) and a list of dashboard pages (`pathSegment`, `apiPrefix`, labels). Sidebar links and routes are **`/dashboard/{integrationId}/{pathSegment}`**. Hermes resolves the active integration by id and calls that integration’s HTTP API for `table-v1` list/meta and mutations.
- **Database-driven schedules** — Schedules are stored in the `Schedule` table. The **hermes-worker** app runs a DataQueue cron job, polls for due schedules, and for each pipeline step expands that step's input (e.g. data-source expressions like `db:ticker:id`), then invokes the step via HTTP. The dashboard does not run the queue.
- **Manual run with execution history** — Trigger a pipeline run from the dashboard and persist it as a first-class execution row (same enqueue/run statuses, step rollups, and invocation rows as other run sources).
- **Session-based auth** — Dashboard uses cookie/session auth. When running pipelines manually, agents are invoked with **short-lived JWT bearer tokens** minted via agent-auth-api using **`HERMES_INTERNAL_API_KEY`**; that preset is never sent to agents.
- **Admin accounts** — Users in the orchestration DB with `role = ADMIN` and `isActive = true` may log in. The dashboard layout re-checks the database on each load so disabled or demoted accounts lose access immediately (cookies are cleared). From **`/dashboard/admins`**, an active admin can add admins (email, name, initial password), reset passwords, enable/disable logins, or delete another admin. You cannot delete yourself, delete the last remaining admin row, disable yourself, or disable the last **active** admin. Deleting an admin removes their API keys first. Bootstrapping the first admin still uses `pnpm create:admin` from `apps/hermes/dashboard` when no UI is available.
- **Variable management** — Admins can CRUD **variables** (key, value, optional note, secret flag) from `/dashboard/variables`. Variables are referenced in agent config and step input as `{{VAR_KEY}}`; at pipeline execution time the placeholder is replaced with the stored value. Secret variables are never returned by the API or shown in the UI after creation (value is masked).
- **Domain integrations** — Admins create an integration (stable key + description); Hermes generates an API key, shows it once, stores it encrypted, and ties pipelines/agents to that integration after the domain service registers with Hermes.

For **this monorepo’s** Mediapulse-specific dashboard surfaces (imports, vocabulary tables, env), see [Mediapulse wiring in this repo](/integration/mediapulse-wiring).

## Key routes / entrypoints

- Dashboard: `/dashboard` (Hermes-native: pipelines, agents, **agent configs**, **variables**, **domain integrations**, **schedules**, **admins**). Domain-owned tables live under **`/dashboard/{integrationId}/{pathSegment}`** (see each integration’s manifest).
- Pipeline actions: create, update, delete, add/remove/reorder steps, run pipeline. **Pipeline detail** uses a three-column layout: available agents (click to add), pipeline steps (select, reorder, remove), and step editor (pipeline name/description, step **input** and **config** from agent schemas). The same page now also shows a unified **Executions** table that merges runs from schedules, HTTP triggers, and manual dashboard runs. When adding or editing a step, you can set input and config (or choose a **saved agent config**). String fields in the step editor use a **variable/expansion input**: you can type freely or use the **Insert…** picker to add variable placeholders (`{{KEY}}`) or data source expansion template strings. Save persists pipeline metadata and the selected step's input/config.
- **Agent configs** (`/dashboard/agent-configs`): Create, edit, duplicate, or delete named configs per agent (agentId + version). Each config has a name, description, and JSON validated against the agent’s config schema. Config string fields support the same variable (`{{key}}`) and data-source expansion insert picker used by pipeline step input forms. Configs can be assigned to pipeline steps so one config is reused across steps; updating a saved config applies to all steps that reference it. If an agent’s config schema changes (same version), saved configs are marked “Schema changed” until you re-save them.
- **Variables** (`/dashboard/variables`): Create, edit, delete. Each variable has a unique key, value, optional note, and “Secret” flag. Use `{{KEY}}` in pipeline step **input** / **config** or saved agent configs; `@hermes/scheduler` substitutes values when a run is planned. Secret values are never returned or shown after save.
- **Data source expansions** (`/dashboard/{integrationId}/data-source-expansions` when the integration has `expand-step-inputs`): Create, edit, delete saved expansion templates (stored in orchestration). Use **Run preview** on the create/edit page where available (calls the domain API). See [Data source expansion](/integration/data-source-expansion) for format and behavior.
- **Domain integrations** (`/dashboard/domain-integrations`): Create integrations; copy the generated API key once into your domain service and agent env (see [Development](/guide/development) for local setup).
- Schedule actions: create, update, delete. Schedules can run **once** (use start date as next run) or **repeating** (cron expression or interval in ms). Next-run computation uses `@hermes/scheduler`; execution runs in hermes-worker.
- **Admins** (`/dashboard/admins`): List dashboard admins, add user with `ADMIN` role, reset password, enable/disable login, delete (with safeguards above).
- Logout: `/logout`.

## Pipeline status and schedules

Each pipeline has a **status** shown on `/dashboard/pipelines`:

- **Incomplete** — One or more steps fail validation (e.g. missing required input/config, invalid data-source expressions). Fix in the pipeline editor.
- **Disabled** — Pipeline is inactive (`isActive` off). Enable it in the pipeline form to use it in schedules.
- **Enabled** — Pipeline is active and all steps pass validation. Only enabled pipelines can be assigned to schedules.

When creating or editing a **schedule**, the pipeline dropdown lists all pipelines but only **enabled** ones are selectable; incomplete or disabled pipelines appear with a suffix and are disabled. The server rejects create/update if the chosen pipeline is not enabled.

If a pipeline becomes not enabled (e.g. you turn it off or a step breaks validation), all schedules that reference that pipeline are **automatically marked disabled** so hermes-scheduler will not run them. Re-enable the pipeline (and fix validation if needed), then re-enable the schedule if desired.

To backfill existing data once: from `apps/hermes`, run `pnpm exec tsx scripts/backfill-disable-schedules-for-invalid-pipelines.ts` to disable any schedule whose pipeline is not enabled.

## Scheduler (hermes-worker)

Hermes **does not** run the DataQueue queue or migrations. To run the scheduler:

1. Run the **hermes-worker** app on a persistent server (e.g. `pnpm dev:hermes-worker` from repo root). It initializes the queue, ensures the `hermes-check-schedules` cron exists, and runs the processor + supervisor.
2. Run DataQueue migrations from **hermes-worker**: `pnpm --filter @hermes/worker run migrate-dataqueue` (or from `apps/hermes-worker`: `pnpm run migrate-dataqueue`). Use the same DB as Hermes with `?schema=dataqueue`.
3. Set `PG_DATAQUEUE_DATABASE`, `ORCHESTRATION_DATABASE_URL`, **`HERMES_INTERNAL_API_KEY`**, and **`AGENT_AUTH_API_URL`** where hermes-worker runs.

See [hermes-worker](/hermes/apps/hermes-worker) for details.
