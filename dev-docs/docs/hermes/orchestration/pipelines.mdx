A **pipeline** is a named workflow scoped to one [domain integration](/hermes/integration/integrate-domain-with-hermes). It runs a sequence of **steps**; each step targets a registered agent version and carries JSON **input** and **config** shaped by that agent’s schemas.

## What defines a pipeline

- **Domain integration**: Every pipeline belongs to exactly one integration. Step agents must be registered for that same integration.
- **Steps**: Ordered by `order`. An **agent step** references `agentId`, `agentVersion`, optional saved **agent config**, and JSON `input` / `config` (see [step input syntax](/hermes/packages/hermes-step-input-syntax)). A **pipeline step** runs another pipeline (see [Pipeline steps](#pipeline-steps)).
- **Active**: When `isActive` is off, the pipeline is treated as disabled for scheduling and similar flows (see [pipeline status](#pipeline-status) below).
- **Description & metadata**: Optional fields for operators; execution-specific options can use `executionConfig` where the product supports it.
- **Agent request timeout** (optional, milliseconds): Upper bound for each agent HTTP POST during a run. Applies to **Run pipeline**, **schedules**, and **HTTP triggers** for this pipeline. When unset, Hermes uses a five-minute default.

## Pipeline steps

A pipeline step points at another pipeline in the same domain integration. When a run is planned, Hermes replaces the step with that pipeline's steps, in order, so one run executes both pipelines back to back. Nested pipeline steps are expanded the same way, up to three levels deep.

The step's `input` holds **overrides**. Each key is merged into the input of every inlined step, replacing the value that step saved. With nesting, the outermost override wins. A common use is scoping a pipeline to one item for a single run:

```json
{ "itemId": "{{params.itemId}}" }
```

Each inlined step keeps its own saved config, contract and its own pipeline's agent request timeout. The run keeps one execution record, and its detail page labels inlined steps with the pipeline they came from, for example `Collection › collector@1.2.0`.

Planning fails, and the run records the reason, when:

- the target pipeline is missing or belongs to another domain integration,
- the pipelines form a cycle,
- nesting goes deeper than three levels,
- or the same step would be reached twice, for example by including one pipeline in two places.

A pipeline that another pipeline uses as a step can't be deleted until those steps are removed. The target pipeline's own **Active** flag is ignored when it is included. Only the pipeline being run decides.

Pipeline steps are created through the orchestration database for now. The pipeline detail page shows them read-only with a link to the target.

## Editing and running

The dashboard provides:

- A **Pipelines** list with create/edit and row actions.
- A **pipeline detail** view to add, reorder, and edit steps, pick agents from the registry, and fill inputs using the JSON schema form when available.
- **Run pipeline** for a manual execution, plus **Executions** and per-execution detail (steps, status, errors).

Related admin surfaces now include reverse links into pipelines:

- **Variables** edit modal: **Used in pipelines** tab for `{{KEY}}` references in step JSON, saved step-linked agent configs, and pipeline `executionConfig`.
- **Data source expansions** edit page: **Used in pipelines** section for exact `db:...` string references (scoped by domain integration).

## Pipeline status

The UI derives a **status** from validation and `isActive`:

- **Incomplete**: Validation failed (for example missing agent in registry, schema errors, or invalid data source expressions in step input). Those pipelines are not safe to schedule or run until warnings are addressed.
- **Disabled**: Valid but `isActive` is false.
- **Enabled**: Valid and active.

Empty pipelines (no steps) validate as complete; add steps before relying on them in production.

## How schedules and HTTP triggers use pipelines

[Schedules](/hermes/orchestration/schedules) and [HTTP triggers](/hermes/orchestration/http-triggers) both reference a **single pipeline** to run. Multiple schedules or triggers can point at the same pipeline. **Run pipeline** from the dashboard targets one pipeline as well. [Variables](/hermes/orchestration/variables) are resolved when a run is planned (including manual runs), before agent jobs are created or invoked.
