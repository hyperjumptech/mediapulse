HTTP triggers let admins run a pipeline on demand through a dedicated endpoint.

## What admins can configure

- `enabled`: disables or enables the trigger without deleting it.
- `auth`: bearer token (admin provides token value during create/update).
- `method`: one HTTP method (`GET`, `POST`, `PUT`, `DELETE`, `PATCH`).
- `pipeline`: the pipeline to run when the endpoint is called.

Multiple HTTP triggers can point to the same pipeline.

## Invoke flow

1. Caller sends a request to `{dashboardOrigin}/api/http-triggers/:triggerId/invoke` (the Next.js API route on the Hermes dashboard app; there is no `basePath` on that app—use your deployed dashboard base URL).
2. Hermes validates:
   - trigger exists and is enabled
   - request method matches trigger config
   - `Authorization: Bearer <token>` matches configured token hash
3. Hermes captures a **request snapshot** (method, full URL, path, query string, all headers with known credential headers redacted, body when safe to read, and common client/proxy headers such as `User-Agent` and `X-Forwarded-For`) and stores it on the new execution row’s `metadata` JSON field (`requestSnapshotVersion: 1`). JSON bodies are parsed and sensitive keys are masked before storage. Bodies are capped at **256 KiB** UTF-8 (truncation is recorded in metadata). Bodies with `multipart/*`, `application/octet-stream`, or major `image`/`video`/`audio` types are not inlined; metadata records the content type and an omit reason instead. TLS version, HTTP protocol version, and the true TCP client address are **not** available from the standard `Request` object in the App Router—only what the request URL and headers provide.
4. Hermes returns **`202 Accepted`** with JSON `{ status: "accepted", executionId }` (wrong method → **405**, disabled trigger → **409**, bad/missing token → **401**, unknown id → **404**).
5. Worker picks up the `execute_http_trigger` DataQueue job and runs the pipeline asynchronously (same planning and variable substitution as schedules).

## Run parameters

A caller can pass values for a single run by sending a JSON body with a `params` object:

```bash
curl -X POST "{dashboardOrigin}/api/http-triggers/:triggerId/invoke" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"params":{"itemId":"abc-123"}}'
```

Step `input` and `config` reference them as `{{params.itemId}}`. A string that is exactly one placeholder takes the parameter's type, so `"{{params.limit}}"` becomes the number `5` when the caller sends `"limit": 5`. A placeholder inside a longer string is replaced with the value as text.

Rules:

- `params` is a flat object of at most 32 keys. Keys start with a letter and contain only letters, digits and underscores.
- Values are strings (up to 2048 characters), numbers or booleans. The whole object must serialize to at most 16 KiB.
- An invalid `params` object returns **400** and no execution is created. A body without `params` works as before.
- A step that references a parameter the run did not receive fails planning with `Run parameter "itemId" is not set`, so an agent never sees an unresolved placeholder.

The parameters are stored on the execution and shown in a **Run parameters** panel on the execution detail page. The dashboard run-pipeline action and the `hermes_mutate_run_pipeline` MCP tool accept the same `params` object.

## Domain events

A trigger can be started by an event from a domain integration instead of by a call to its URL. Pick **An event sent by a domain integration** under **Started by** and enter an event name such as `order.created`. Event triggers have no URL, token or method.

The domain integration sends the event with the same API key it uses to register with Hermes:

```bash
curl -X POST "{dashboardOrigin}/api/domain-integrations/events" \
  -H "Authorization: Bearer <domain integration API key>" \
  -H "Content-Type: application/json" \
  -d '{"event":"order.created","params":{"orderId":"o-1"}}'
```

Hermes starts one run for each enabled event trigger with that name whose pipeline belongs to the calling integration, and passes `params` as [run parameters](#run-parameters). It answers **202** with `{ "executions": [{ "triggerId", "executionId" }] }`. The list is empty when nothing listens to the event, so the domain can tell that it is not configured. A wrong key returns **401** and an invalid event name or `params` returns **400**.

Disable or delete the trigger to stop reacting to the event. Nothing changes on the domain side.

## Execution history

The dashboard includes:

- `HTTP Triggers` list page for CRUD
- trigger detail page with executions table
- execution detail page with step rollups, invocation-level status/errors, and a **Request snapshot** panel (JSON, with an extra masking pass for display)

This mirrors the schedules execution experience, but is on-demand instead of periodic.
