## Purpose

`/dashboard/{integrationId}/entity-types` (for example `/dashboard/mediapulse/entity-types`) is where admins define the controlled vocabulary used by the analysis agent to classify extracted entities in article text. The integration id and page list come from the domain integration registration manifest.

Good examples: `COMPANY`, `PERSON`, `SECTOR`, `PRODUCT`, `TOPIC`, `EVENT`.

This page directly influences:

- classification consistency in `entity.type_id`
- extraction quality in `article_entity`
- graph quality for `ticker_entity` and `entity_relation`

## Common confusion to avoid

`entity_type` is a category definition, not an extracted mention and not a graph edge:

- `entity_type`: "What kind of thing is this?" (for example `COMPANY`)
- `entity`: "Which concrete thing is this?" (for example `Apple Inc.`)
- `article_entity`: "Where was this entity mentioned?" (article evidence)
- `ticker_entity`: "Is this entity part of ticker X graph context?"
- `entity_relation`: "How does this entity connect to another entity?"

If you are adding a new row in this page, ask: "Am I defining a reusable class label?" If not, it likely belongs in a different table.

## Data contract

Rows map to the `entity_type` table in database schema:

| Field         | Required           | Database behavior   | Guidance                                                 |
| ------------- | ------------------ | ------------------- | -------------------------------------------------------- |
| `name`        | Yes                | Unique (`@unique`)  | Use uppercase snake-style token, stable over time        |
| `description` | No but recommended | Prompt context only | Define boundaries and include positive/negative examples |

## How analysis uses entity types

During analysis:

1. Agent-data-api returns the full entity-type list.
2. The list is injected into extraction prompts.
3. The model must choose one of these labels for each extracted entity.
4. Results are upserted into `entity` with a concrete `typeId`.

If definitions are vague, extraction quality drops quickly.

## Naming and modeling conventions

- Use semantic categories, not implementation details.
- Keep names short and specific (`REGULATOR` instead of `EXTERNAL_PARTY_TYPE_A`).
- Avoid near-duplicates (`COMPANY` and `ORGANIZATION`) unless you can define strict boundaries.
- Do not encode sentiment in the type (`NEGATIVE_EVENT`); use relation or metadata instead.
- Prefer adding detail in `description` before adding new types.

## Description template (recommended)

For each type, write description in this structure:

1. Definition: what the type is.
2. Include: 2-4 concrete examples.
3. Exclude: similar things that should map elsewhere.
4. Rule of thumb: one short heuristic sentence.

Example for `PERSON`:

"Human individual relevant to company operations or market narrative. Include CEO, CFO, board members, regulators speaking in personal capacity. Exclude company names and institutions."

## Change management workflow

1. Propose type changes in a small batch.
2. Update descriptions first.
3. Run analysis on sample tickers and inspect extracted entities.
4. Verify score quality impact in `article_relevance`.
5. Merge only when labels are stable and interpretable.

## Operational notes

- Keep type names stable after production use for analytics continuity.
- Prefer deprecating in docs/process before deleting rows that are referenced by `entity`.
- If quality drifts, adjust descriptions first, then evaluate if new type creation is truly needed.
- Review the long-tail entities regularly to catch ambiguous labels.

## Why it matters

Entity types are foundational KG vocabulary. Better type quality improves:

- entity deduplication and canonicalization
- relation extraction precision
- relevance scoring signal quality (`entityOverlap`)
- newsletter coherence and explainability
