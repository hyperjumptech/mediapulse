## Overview

MediaPulse uses a per-ticker knowledge graph (KG) to turn raw news into structured signals for newsletter generation.

At a high level, the KG lifecycle is:

1. **Expand target tickers** from enabled subscriptions.
2. **Generate search queries** for each ticker context.
3. **Collect and store raw articles** from those queries.
4. **Extract entities and relations** from article text.
5. **Compute relevance scores** per article and ticker.
6. **Select top articles** and generate newsletter content.
7. **Deliver newsletters** and repeat on schedule.

Ticker fan-out uses [data source expansion](/integration/data-source-expansion) in pipeline step input, for example:

`{ "tickerId": "db:userTicker:tickerId?where.enabled=true" }`

Each step runs once per enabled `user_ticker` row (or per distinct ticker if you add `distinct=tickerId`).

**During development**, load default KG rows using:

- `pnpm --filter @mediapulse/database run seed-kg-vocabulary` (from the monorepo root) — upserts default **entity types** and **relation types** in the Mediapulse domain DB.
- `pnpm seed-kg-pipelines` — from `apps/hermes/dashboard`, upserts the **pipelines** and **schedules** in the table above in the Hermes orchestration DB.

Both operations are idempotent and safe to re-run. For an empty local DB, run vocabulary first so the dashboard and analysis agents have the baseline vocabulary; then run the pipeline seed.

## Data model in detail

### Terminology you should keep distinct

These terms are related but represent different layers of the KG:

| Term                               | What it means                                                              | Typical example                                       |
| ---------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------- |
| `entity_type`                      | A **category label** for entities (vocabulary/admin-defined).              | `COMPANY`, `PERSON`, `PRODUCT`                        |
| `entity`                           | A **canonical real-world thing** (a node in the graph).                    | `Apple Inc.`, `Tim Cook`, `iPhone 16`                 |
| `ticker_entity`                    | A **membership link** saying an entity belongs to one ticker's KG context. | `AAPL` graph contains entity `Apple Inc.`             |
| `article_entity`                   | A **mention link** saying a specific article mentions an entity.           | Article `data_source:123` mentions `Tim Cook` 4 times |
| `relationship` (`entity_relation`) | A **typed directed edge** between two entities.                            | `Tim Cook --CEO_OF--> Apple Inc.`                     |

In short:

- `entity_type` classifies an `entity`.
- `ticker_entity` scopes an `entity` to a ticker graph.
- `article_entity` links an `entity` to article evidence.
- `entity_relation` links one `entity` to another `entity`.

### Core ingestion tables

| Table          | Purpose                                                                       | Produced by        |
| -------------- | ----------------------------------------------------------------------------- | ------------------ |
| `search_query` | Stores generated search strings per ticker.                                   | Query-analysis     |
| `data_source`  | Stores collected article/page payloads (`url`, `title`, `content`, metadata). | Data-collection    |
| `newsletter`   | Stores generated newsletter content per ticker/day.                           | Content-generation |

### KG vocabulary (admin-curated)

| Table           | Purpose                                                             | Managed from                                 |
| --------------- | ------------------------------------------------------------------- | -------------------------------------------- |
| `entity_type`   | Allowed classes for canonical entities (`COMPANY`, `PERSON`, etc.). | `/dashboard/{integrationId}/entity-types`   |
| `relation_type` | Allowed labels for edges (`CEO_OF`, `PARTNER_OF`, etc.).            | `/dashboard/{integrationId}/relation-types` |

### KG structure tables

| Table               | Purpose                                                          | Notes                                                               |
| ------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| `entity`            | Canonical node (`canonical_name`, `type_id`, optional metadata). | One real-world concept per row.                                     |
| `entity_alias`      | Alternate spellings/aliases for entity matching and dedup.       | Indexed by `normalized_alias`.                                      |
| `ticker_entity`     | Membership of entities in a ticker graph.                        | Not a new entity row; it links existing `ticker` + `entity`.        |
| `entity_relation`   | Directed typed edge from one entity to another.                  | "Relationship" table; unique by `(from, to, relation_type)`. Hermes: `/dashboard/{integrationId}/entity-relations` (create, edit, delete, view detail, **Reset all**). |
| `article_entity`    | Mentions linking article (`data_source`) to extracted entities.  | Evidence table; one row means "this article mentioned this entity". |
| `article_relevance` | Per-ticker article score and selection state.                    | Includes `score_breakdown` JSON.                                    |

## End-to-end flow for one ticker

1. **Query-analysis** reads ticker profile and existing KG context.
2. It upserts multiple rows into `search_query`.
3. **Data-collection** reads queries and persists fetched articles into `data_source`.
4. **Analysis** reads unprocessed sources and current vocab (`entity_type`, `relation_type`).
5. Analysis extracts entities and relations, then upserts:
   - `entity` and `entity_alias`
   - `ticker_entity`
   - `entity_relation`
   - `article_entity`
6. Analysis computes relevance per `(data_source_id, ticker_id)` and upserts `article_relevance`.
7. Top-K rows are marked `selected = true`.
8. **Content-generation** reads selected rows and creates `newsletter`.
9. **Delivery** reads newsletter + subscribers and sends messages.

## Relevance scoring model (analysis agent)

The **article-analysis** agent computes a **weighted composite score** in `[0, 1]` per `(data_source_id, ticker_id)` and persists subscores in `article_relevance.score_breakdown` JSON.

**Canonical v1 keys** (required for each scored article; align with downstream charts):

| Key               | Description |
| ----------------- | ----------- |
| `breakingNews`    | Breaking / urgent / market-moving cues from title and body heuristics |
| `kgRelation`      | Signal from extracted relation count |
| `fundamental`     | Filings, earnings, guidance, and similar keywords |
| `tickerSalience`  | Mentions and extracted entity coverage |
| `sourceQuality`   | Host-tier trust prior |
| `_version`        | Integer breakdown version — set via Hermes agent config **`scoreBreakdownVersion`** (must match stored JSON when bumping schema) |

`score = sum_k relevanceWeight_k * scoreBreakdown[k]` over the five dimensions (default weights `0.2` each; tune via Hermes **`relevanceWeight*`** keys on article-analysis).

Top-scoring rows that pass **`relevanceMinScore`** are candidates for **`selected = true`**, up to the **remaining daily budget**: `maxSelectedRelevancePerTickerPerDay - selectedCountToday`, where `selectedCountToday` is returned on **`GET /api/v1/analysis`** as **`relevanceSelectionState.selectedCountToday`** (UTC day start in **`utcDayStartIso`**). Content-generation consumes **`selected`** rows scored today.

## Selection policy and tie-breakers

When assigning **`selected`** in a batch:

1. Higher `score`
2. Newer `data_source.createdAt` at equal `score`
3. Respect the daily cap above

If no row crosses **`relevanceMinScore`**, all rows may remain `selected = false` for that run; content-generation should skip with a clear status instead of producing low-signal output.

## Extraction quality guidelines

- Keep entity and relation vocabularies compact and explicit.
- Avoid overlapping entity types (for example, `ORGANIZATION` and `COMPANY`) unless you have a strict distinction.
- Treat relation types as typed verbs and keep direction consistent (`CEO_OF` from person to company).
- Update descriptions whenever extraction drift appears in production samples.

## Operational playbook

### What to monitor

- Number of generated `search_query` rows per ticker/day.
- `data_source` ingestion volume and source diversity.
- `article_relevance` score distribution and selected count.
- Newsletter skip rate (no selected articles).
- Growth of KG nodes/edges (`entity`, `entity_relation`) by ticker.

### Common failure patterns

| Symptom                    | Likely cause                          | First checks                                              |
| -------------------------- | ------------------------------------- | --------------------------------------------------------- |
| Very few selected articles | Strict scoring or weak query coverage | Check search query quality and source volume              |
| Repetitive newsletters     | Selection cap or weak salience signals  | Inspect `score_breakdown.tickerSalience` + source spread  |
| Wrong entity labels        | Ambiguous entity type definitions     | Refine `entity_type.description`                          |
| Nonsensical relations      | Directionality confusion in labels    | Clarify relation semantics in `relation_type.description` |

### Safe maintenance actions

- Re-run `seed-kg-pipelines.ts` (idempotent) after schedule/pipeline drift.
- Add or improve vocab descriptions before adding many new labels.
- Backfill analysis by re-running pipeline C for selected tickers/date windows.
- Keep relation/entity names stable to preserve historical analytics continuity.
