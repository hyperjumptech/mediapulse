## Purpose

Given a `tickerId`, the query-analysis agent produces a small set of search queries that actually return results. The set covers the issuer itself, its named competitors, its regulators, and the industry and global topics that move it.

This is version 3.0.0, a self-driving pipeline. It no longer leans on a knowledge-graph context payload or on operator-tuned prompt templates. It discovers the entities that matter, phrases queries around them, and keeps only the ones that a real search provider answers.

## Required contract

The agent runs with `requireContract: true`. A run without a contract brief, or with a blank one, returns HTTP 400 before `run` is ever called. The message tells the operator to attach an Agent Contract to the pipeline step.

The brief is the steering context for discovery. Before the discovery LLM call, the runtime wraps the brief in a `<product_contract>` block and prepends it to the system prompt, so the model knows which competitors and regulators count as real signal for this reader. The pipeline step's `agentContractId` must be set in Hermes for the brief to reach the agent.

<Callout type="info">
  The exact brief this agent expects, a clause-by-clause rationale, and how to
  attach it in the Hermes dashboard live on the [Query Analysis Contract
  Brief](/mediapulse/apps/agents/query-analysis-contract-brief) page.
</Callout>

## I/O contract

- **Input:** `{ tickerId: string }`
- **Reads:** the agent-data-api `query-analysis` GET resource for the ticker
- **Writes:** the agent-data-api `query-analysis` POST resource (persists the active query set)

The GET response now carries only the ticker. There are no more KG entities, themes, peers, calendar, or headline samples.

### GET response fields

| Field    | Shape                                                                                   | Notes                    |
| -------- | --------------------------------------------------------------------------------------- | ------------------------ |
| `ticker` | `{ id, symbol, name, sector?, industry?, subSector?, subIndustry?, businessActivity? }` | The tracked issuer only. |

### POST body

Each persisted query is `{ text, intent, rank }`. The agent sends the ranked set alongside `generationSource: "self_driving_v1"`, the run `strategySnapshot`, and `activate: true` so the new set becomes the active one. The response returns `created`, `createdSetId`, and `activeSetId`.

## Run flow

The pipeline lives in `src/run.ts` and its stage folders (`src/pipeline`, `src/keywords`, `src/discovery`, `src/probe`, `src/select`).

<Steps>
  <Step>
    ### Load the ticker

    GET the `query-analysis` resource for `tickerId` and read the ticker's
    identity and classification (sector, industry, sub-sector, sub-industry,
    business activity).

  </Step>
  <Step>
    ### Look up the discovery cache

    Check the per-ticker `ticker_discovery` cache via the agent-data-api SDK
    (`tickerDiscoveryLookup`). A hit returns the cached competitors and
    regulators and skips the LLM call.

  </Step>
  <Step>
    ### Discover on a miss

    On a cache miss or expiry, `discoverEntities`
    (`src/discovery/discover-entities.ts`) makes a single `generateObject` call,
    steered by the contract brief, to name the competitors and regulators. It
    runs with `maxRetries: 0` and degrades to empty (own-company plus industry
    only) if the call fails, so discovery never blocks the run. The result is
    written back with `tickerDiscoveryRecord` at a fourteen-day TTL.

  </Step>
  <Step>
    ### Build candidates

    Build candidate queries from four stages, own-company, competitors,
    regulators, and industry, in both Indonesian (`id`) and English (`en`).

  </Step>
  <Step>
    ### Yield-probe

    Probe each candidate through the search provider pool
    (`src/probe/yield-probe.ts`, reusing `@workspace/agent-search`
    `countQueryHits`). Dedupe by normalized text, cap to the probe budget by
    stage priority, drop anything that returns zero results, and rank the rest
    by hit count.

  </Step>
  <Step>
    ### Finalize and persist

    `finalizeQueries` (`src/select/finalize.ts`) guarantees at least one
    surviving query for every dedicated newsletter section, keeps the id/en
    mix, and caps the set at 24. The agent then POSTs the active set with
    `generationSource: "self_driving_v1"`.

  </Step>
</Steps>

## Hermes config

The agent exposes only two flat groups, the same shape data-collection uses. Everything else is an internal constant, not an operator knob.

### `web_search`

An array of `{ provider, apiKey }` entries for the yield probe. Supported providers are `serper`, `tavily`, and `exa`. The probe rotates the starting provider round-robin and falls back to the rest on failure. The default pool is all three, keyed by Hermes variables (`{{SERPER_API_KEY}}`, `{{TAVILY_API_KEY}}`, `{{EXA_API_KEY}}`).

### `ai`

LLM credentials for entity discovery: `{ apiKey, model, baseUrl }`, defaulting to `{{AI_API_KEY}}`, `{{AI_MODEL}}`, and `{{AI_BASE_URL}}`. The base URL points at any OpenAI-compatible endpoint (for example an OpenRouter gateway).

<Callout type="warn">
  There is no personas, exemplars, diversity gate, `intentWeights`,
  `templatePack`, or creativity-sampling config anymore. Languages (`id` plus
  `en`), probe locales, the query count of 24, discovery caps (6 competitors, 4
  regulators, 2 keywords per entity), probe budget and concurrency, cache TTL,
  and the Indonesia/IDX market anchors are all internal constants in
  `src/constants.ts`. Change them with a code deploy, not a Hermes config edit.
</Callout>

## Query intents and section mapping

Every persisted query carries an `intent`, and each intent maps to the newsletter section it feeds. The old `source` field (deterministic/llm/curated) is gone. The pipeline emits the intents below.

| Intent             | Feeds section                                       | Stage       |
| ------------------ | --------------------------------------------------- | ----------- |
| `breaking`         | Industry Pulse or Quick Hits (no dedicated section) | Own-company |
| `deals`            | Deals & Movements                                   | Own-company |
| `competitor`       | Competitive Landscape                               | Competitors |
| `regulatory`       | Regulatory & Policy Watch                           | Regulators  |
| `industry_trend`   | Industry Pulse                                      | Industry    |
| `technology_trend` | Disruptors / Tech                                   | Industry    |
| `macro`            | Industry Pulse or Quick Hits (no dedicated section) | Industry    |
| `wildcard`         | Industry Pulse or Quick Hits (no dedicated section) | Industry    |

The intent-to-section map is the authoritative `SECTION_BY_INTENT` record in `@workspace/agent-data-api-contract`. Finalization reads it to guarantee that every section with a dedicated intent keeps at least one query. Stage priority also drives the probe budget cap: own-company first, then competitors, then regulators, then industry.

## Discovery cache

Competitor and regulator discovery is the one LLM step, and it is cached per ticker in `ticker_discovery` so a daily fan-out does not re-pay for it every run.

- **Lookup:** `tickerDiscoveryLookup` returns the cached entry, or `null` on a miss or expiry.
- **Write:** `tickerDiscoveryRecord` stores the competitors, regulators, and the discovery model at a fourteen-day TTL.
- **Freshness:** a single `expiresAt` timestamp. Past it, the next run treats the ticker as a miss and rediscovers.

A cache hit skips the LLM call entirely and reuses the stored entities, so most runs cost only the yield probe.

## Yield probe

The probe is what makes the output queries return real results. It reuses `countQueryHits` from `@workspace/agent-search` to count hits per candidate across the Indonesian and global (English) locales.

1. **Dedupe** candidates by normalized text.
2. **Cap** to the probe budget, keeping higher-priority stages first.
3. **Drop** any candidate that returns zero results.
4. **Rank** the survivors by hit count.

Finalization can reinstate the highest-yield dropped candidate for a starved dedicated section, so section coverage is never sacrificed to the zero-result rule.

## Chronicle telemetry

Each run writes a `strategySnapshot` for the newsletter Chronicle:

- **Discovery:** model and token usage (prompt, completion, total, call count) plus a `cacheHit` flag.
- **Search:** provider names with per-provider call counts (`providerUsage`) and total `searchCredits`.
- **Discovered entities:** the competitor and regulator names in play.
- **Probe counts:** candidates, deduped, dropped-zero-yield, and survivors.
- **Output:** the query breakdown by intent and section, the id/global split, and the final query texts.
- **Timing:** total, discovery, probe, and finalize durations.

The newsletter Chronicle surfaces the search provider, credits, and discovery tokens from this snapshot.
