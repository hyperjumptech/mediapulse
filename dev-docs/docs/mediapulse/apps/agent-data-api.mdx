## Purpose

agent-data-api is a Hono server that exposes data endpoints used by agents. **The agent gets data it needs and stores output data it produces to this API via the agent-data-api-client SDK.** All routes are protected by bearer auth; the token is verified via `@workspace/agent-auth-client` against agent-auth-api.

## Features

agent-data-api is the **HTTP persistence layer between agents and the database**: agents do not talk to Prisma directly. Each resource is a small, typed surface with **GET** (load state for a run or ticker) and **POST** (save the next artifact), backed by shared Zod schemas in `@workspace/agent-data-api-contract`.

- **Bearer auth** — Requests must send `Authorization: Bearer <jwt>` (the same short-lived invocation JWT Hermes sends to agents). Verified with agent-auth-api `POST /api/verify` via `verifyTokenViaAuthApi`; agents forward the `Authorization` header from their run context to the SDK.
- **Content generation** — Stores and loads generated newsletter-style output so downstream steps can reuse it without reshaping ad hoc payloads.
- **Data collection** — Stores and loads crawled or gathered source material (pages, feeds, etc.) so collection and later stages see the same structured snapshot.
- **Delivery** — Loads the latest newsletter for a ticker, **subscriber emails** and **`userTickerId`** from enabled `user_ticker` rows, plus **`deliveredUserTickerIds`** (existing checkpoints for idempotent replays). When there is no newsletter, **GET returns 200** with `newsletter: null`, `subscribers: []`, and empty checkpoint ids (agents skip without treating the call as an error). **POST** records a **`newsletter_delivery_checkpoint`** after a successful send (`userTickerId`, `newsletterId`, optional Resend id).
- **Delivery run** — **POST** persists one diagnostic run and per-recipient rows (including optional **`runSkipReason`**, Hermes **`jobId` / `hermesExecutionId` / `hermesScheduleId`**, and per-recipient **`errorCategory`**). **GET** lists runs with optional filters (`tickerId`, `outcome`, `start`, `end` — each of `start` / `end` applies **`createdAt` `gte` / `lte` independently** when provided). Used by the delivery agent for Hermes-visible outcomes (`success`, `skipped`, `failed`, `partial_success`). The Mediapulse Hermes **Delivery runs** table supports the same filters via query string (`tickerId`, `outcome`, `start`, `end`) in addition to search (`q`) and sort.

**Contract-driven routing:** URL paths and the `@workspace/agent-data-api-client` method namespaces are derived from `agentDataApiManifest` plus version helpers in `@workspace/agent-data-api-contract` (resource keys → `/api/<version>/...` segments). That keeps the server, SDK, and docs aligned and avoids one-off paths in app or agent code.

## Key routes

Agents should not call these HTTP paths directly. In agent code, use `@workspace/agent-data-api-client` and call SDK namespaces such as `contentGeneration`, `dataCollection`, and `delivery`. The SDK provides typed methods for each endpoint and validates responses with shared schemas.

| Method | Path                                 | Description                                                           |
| ------ | ------------------------------------ | --------------------------------------------------------------------- |
| GET    | `/api/v1/content-generation`         | Get content-generation data (e.g. by tickerId)                        |
| POST   | `/api/v1/content-generation`         | Store content-generation payload                                      |
| GET    | `/api/v1/data-collection`            | Get data-collection data                                              |
| POST   | `/api/v1/data-collection`            | Store data-collection payload                                         |
| GET    | `/api/v1/delivery`                   | Get delivery payload (nullable newsletter, subscribers + checkpoints) |
| POST   | `/api/v1/delivery`                   | Upsert delivery checkpoint after successful send                      |
| GET    | `/api/v1/delivery-run`               | List delivery diagnostic runs (filters optional)                      |
| POST   | `/api/v1/delivery-run`               | Persist one delivery run + recipient outcomes                         |
| POST   | `/api/v1/user-registration-register` | Process a new or returning subscription                               |
| POST   | `/api/v1/user-registration-confirm`  | Confirm a pending subscription (double opt-in)                        |

For example, in agents:

```ts
const dataApiClient = createAgentDataApiClient({
  baseUrl: env.AGENT_DATA_API_URL,
  version: "v1",
  token,
});

await dataApiClient.contentGeneration.get({ tickerId });
```

### Delivery agent (Hermes config + semantics)

- **Config (`configSchema`):** `resendApiKey` (optional; overrides `RESEND_API_KEY`), `resend.from` / `resend.replyTo` / optional **`resend.tags`**, **`send.includeHtml` / `send.includeText`** (defaults `true`; at least one required), `rateLimit.minIntervalMs` + `maxSendsPerMinute`, `retry` (`maxAttempts`, `baseDelayMs`, `maxDelayMs`, `jitter`), `template.newsletterVariant` (`default` only in v1).
- **Pipeline HTTP outcome:** Partial delivery still returns **invoke envelope `status: success`** with `details.outcome: "partial_success"`; full diagnostics live in **delivery runs** (DB + Hermes Mediapulse **Delivery runs** table). All recipients failing returns `status: failure` on the agent response.
- **PII:** Logs use hashed `userTickerId` fragments; persisted diagnostics store `userTickerId` and sanitized error text (not raw emails in optional summary fields).

## Versioning

- `agent-data-api` can serve multiple live versions (for example `v1`, `v2`) under `/api/<version>/...`.
- The contract package defines live versions and the default SDK version (`AGENT_DATA_API_DEFAULT_VERSION`).
- Existing agents can pin a specific version with `createAgentDataApiClient({ version: "v1", ... })` during migrations.

## Port

- **8081** (default from `env.PORT`).

## Workspace dependencies

- `@workspace/agent-auth-client` — `verifyTokenViaAuthApi` for bearer (invocation JWT) auth.
- `@workspace/agent-data-api-contract` — Shared Zod schemas, `agentDataApiManifest`, and derived path helpers.
- `@workspace/agent-data-api-client` — Typed SDK used by agents.
- `@workspace/api-utils` — Error helpers.
- `@mediapulse/env` — Environment (including `AGENT_AUTH_API_URL`).
- `@mediapulse/database` — Prisma for reading/writing agent data.
- `@workspace/logger` — Pino logger.

## Endpoint change workflow

When the API surface changes (new endpoint, removed endpoint, or request/response changes), follow this sequence to keep contract, server routes, SDK, and agents in sync:

1. **Contract first:** update schemas and exported types in `@workspace/agent-data-api-contract`.
2. **Manifest update:** add or update the resource in `agentDataApiManifest` (this is the canonical source of route shape).
3. **API wiring:** implement/update handlers in `apps/mediapulse/agent-data-api/src/routes` and `src/services`, then wire them in the typed handler map used by route registration.
4. **SDK alignment:** update `@workspace/agent-data-api-client` if request/response types changed.
5. **Consumer updates:** update agent callsites that use the SDK.
6. **Validation:** update tests, then run `pnpm code-quality`.

See `.cursor/skills/agent-data-api-endpoints/SKILL.md` for the detailed checklist.
