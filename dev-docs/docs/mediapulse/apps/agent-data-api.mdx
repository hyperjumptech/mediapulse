## Purpose

agent-data-api is a Hono server that exposes data endpoints used by agents. **The agent gets data it needs and stores output data it produces to this API via the agent-data-api-client SDK.** Versioned routes are protected by bearer auth (verified via `@workspace/agent-auth-client` against agent-auth-api), except **user-registration unsubscribe** (GET/POST), **`GET /api/<version>/user-registration-tickers`**, **`POST /api/<version>/user-registration-web-signup`**, and **`GET /api/<version>/user-registration-confirm-subscription`**, which skip bearer verification so the user-registration Next app can call them server-side with only `AGENT_DATA_API_URL` configured.

## Features

agent-data-api is the **HTTP persistence layer between agents and the database**: agents do not talk to Prisma directly. Each resource is a small, typed surface with **GET** (load state for a run or ticker) and **POST** (save the next artifact), backed by shared Zod schemas in `@workspace/agent-data-api-contract`.

- **Bearer auth** — Requests must send `Authorization: Bearer <jwt>` (the same short-lived invocation JWT Hermes sends to agents). Verified with agent-auth-api `POST /api/verify` via `verifyTokenViaAuthApi`; agents forward the `Authorization` header from their run context to the SDK.
- **Content generation** — Stores and loads generated newsletter-style output so downstream steps can reuse it without reshaping ad hoc payloads.
- **Data collection** — Stores and loads crawled or gathered source material (pages, feeds, etc.) so collection and later stages see the same structured snapshot. A companion **existing URLs** POST lets the data-collection agent skip web fetch for URLs already persisted for a ticker (exact URL match).
- **Analysis** — Loads unanalyzed (or full re-score) `DataSource` rows plus KG vocabulary (`entityTypes`, `relationTypes`, `existingEntities`) for the article-analysis agent, and accepts POST payloads that upsert entities, relations, `article_entity`, and `article_relevance` for a ticker. Optional GET bounds (`start`, `end`, ISO 8601) filter `DataSource.createdAt` **server-side** (FR1 / FR2 eligibility windows). Optional **`limit`** caps how many sources are returned (oldest first) while **`dataSourceTotalCount`** reports how many rows matched the filters, so agents can debounce on total backlog without loading every body into memory.
- **Delivery** — Loads the latest newsletter for a ticker, **subscriber emails** and **`userTickerId`** from enabled `user_ticker` rows, plus **`deliveredUserTickerIds`** (existing checkpoints for idempotent replays). When there is no newsletter, **GET returns 200** with `newsletter: null`, `subscribers: []`, and empty checkpoint ids (agents skip without treating the call as an error). **POST** records a **`newsletter_delivery_checkpoint`** after a successful send (`userTickerId`, `newsletterId`, optional Resend id).
- **Delivery claim** — Makes delivery idempotent against **concurrent runs**, not just sequential replays. **`POST /api/v1/delivery-claim`** inserts the checkpoint **before** the send and returns **`{ claimed }`** — `false` when another run already owns the recipient (the unique `(newsletterId, userTickerId)` constraint decides the winner), so the caller skips sending. **`POST /api/v1/delivery-claim-release`** deletes an **unfinalized** claim (one with no `resendEmailId`) and returns **`{ released }`**, so a recipient whose send failed can be retried by a later run. A successful send then calls **`POST /api/v1/delivery`** to fill in the Resend id, which finalizes the row so release can no longer remove it.
- **Delivery run** — **POST** persists one diagnostic run and per-recipient rows (including optional **`runSkipReason`**, Hermes **`jobId` / `hermesExecutionId` / `hermesScheduleId`**, and per-recipient **`errorCategory`**). **GET** lists runs with optional filters (`tickerId`, `outcome`, `start`, `end` — each of `start` / `end` applies **`createdAt` `gte` / `lte` independently** when provided). Used by the delivery agent for Hermes-visible outcomes (`success`, `skipped`, `failed`, `partial_success`, `skipped_all_already_delivered`). The Mediapulse Hermes **Delivery runs** table supports the same filters via query string (`tickerId`, `outcome`, `start`, `end`) in addition to search (`q`) and sort.

**Contract-driven routing:** URL paths and the `@workspace/agent-data-api-client` method namespaces are derived from `agentDataApiManifest` plus version helpers in `@workspace/agent-data-api-contract` (resource keys → `/api/<version>/...` segments). That keeps the server, SDK, and docs aligned and avoids one-off paths in app or agent code.

In agent code, use `@workspace/agent-data-api-client` and call SDK namespaces such as `contentGeneration`, `dataCollection`, `dataCollectionExistingUrls`, `analysis`, `delivery`, `deliveryClaim`, and `deliveryClaimRelease`. ### Content generation (`/api/v1/content-generation`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/content-generation.ts`. Schemas live in `@workspace/agent-data-api-contract` (`content-generation.ts`).

- **GET** — Query: `tickerId` (required). Returns today's selected data sources for the ticker ordered by relevance score, plus `competitors` (ranked peer COMPANY names from `COMPETITOR` / `SECTOR_PEER` KG edges) and `issuerAliases` (ticker symbol, legal name, and KG aliases). Both list fields default to `[]` when the issuer anchor or peer graph is missing.
- **POST** — Body validated by `postContentGenerationBodySchema`. Required fields: `subject`, `content`, `tickerId`. Optional field: `description`. The following optional provenance and token-usage fields are also accepted; all are stored as `null` when omitted (backward-compatible — existing callers that omit these fields continue to work):

| Field              | Type               | Description                                |
| ------------------ | ------------------ | ------------------------------------------ |
| `model`            | `string`           | LLM model name used for generation         |
| `agentVersion`     | `string`           | Agent semver at generation time            |
| `configVersion`    | `string`           | Hermes config version string               |
| `promptHash`       | `string`           | Short hash of effective prompt             |
| `configSnapshotId` | `string`           | Immutable Hermes config snapshot reference |
| `promptTokens`     | `number` (integer) | Prompt token count from LLM response       |
| `completionTokens` | `number` (integer) | Completion token count from LLM response   |
| `totalTokens`      | `number` (integer) | Total token count from LLM response        |

The **GET** response now also carries **`dataSourceId`** (the `data_source` row id) and the lightweight **`description`** on each source. `content` is nullable: after ADR-0002 most sources start with only a `description`, and a full `content` body appears only once content-generation fetches it on demand.

The **POST** response is **`{ message, id? }`** where **`id`** is the created `newsletter` row id. Agents use it to attach follow-up records (translations, citations) to the persisted newsletter.

### Content generation fetched content (`POST /api/v1/content-generation/fetched-content`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/content-generation.ts`. Schemas live in `@workspace/agent-data-api-contract` (`content-generation.ts`); manifest key **`contentGenerationFetchedContent`** (custom path segment `/content-generation/fetched-content`).

Used by the content-generation on-demand fetch (ADR-0003) to persist a fetched body back onto its data-source row so a re-run or another ticker sharing the URL reuses it without re-paying.

- **POST** — Body (`postContentGenerationFetchedContentBodySchema`): a non-empty array (at most **`CONTENT_GENERATION_FETCHED_CONTENT_MAX`**, 50) of **`{ dataSourceId (uuid), content (non-empty), fetchProvider (non-empty), publishedAt? (ISO datetime) }`**. Each item updates the matching `data_source` row's **`content`**, **`fetchedAt`** (now), and **`fetchProvider`**. When **`publishedAt`** is supplied it is written only to rows whose `published_at` is still `NULL`, so a date already resolved at collection is never overwritten. Rows are updated independently; a missing row is skipped without failing the batch. Response: **`{ updatedCount }`**.

Most Indonesian publishers put no date in the URL path, so collection resolves `published_at` for only a minority of rows. The fetched body carries the date in `article:published_time` or JSON-LD `datePublished`, and the agent extracts it there via `extractPublishedDate`. Without this backfill the per-section freshness ceilings and the same-day event-dedup path both no-op on a null date.

From agents, use SDK namespace **`contentGenerationFetchedContent`**: **`create`** for POST.

### Content generation fetch events (`POST /api/v1/content-generation/fetch-events`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/fetch-event.ts`. Schemas live in `@workspace/agent-data-api-contract` (`content-generation-fetch-event.ts`); manifest key **`contentGenerationFetchEvents`** (custom path segment `/content-generation/fetch-events`).

Records a durable `fetch_event` row per on-demand Fetch so credit spend is auditable against the model's stated reason (ADR-0005). One event is written for every requested-and-attempted source.

- **POST** — Body (`postContentGenerationFetchEventsBodySchema`): a non-empty array (at most **`CONTENT_GENERATION_FETCH_EVENTS_MAX`**, 100) of **`{ dataSourceId (uuid), tickerId (non-empty string), reason (string), provider? (non-empty string), status }`** where **`status`** is one of `succeeded`, `gate_dropped`, `fetch_failed`. `provider` is omitted when the fetch failed. Rows are inserted independently; a failed insert is skipped without failing the batch. Response: **`{ recordedCount }`**.

From agents, use SDK namespace **`contentGenerationFetchEvents`**: **`create`** for POST. The content-generation agent posts these best-effort after its fetch step; a recording failure never fails the newsletter.

### Content generation citations (`POST /api/v1/content-generation/citations`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/newsletter-citation.ts`. Schemas live in `@workspace/agent-data-api-contract` (`newsletter-citation.ts`); manifest key **`contentGenerationCitations`** (custom path segment `/content-generation/citations`).

Persists the newsletter bullet to cited Data Source link that citation grounding computes, as a queryable `newsletter_citation` relation (ADR-0005), so a delivered Newsletter can be traced back to its sources.

- **POST** — Body (`postContentGenerationCitationsBodySchema`): **`{ newsletterId (uuid), citations: [{ dataSourceId (uuid), sectionKey (non-empty string) }] }`** (at most **`NEWSLETTER_CITATIONS_MAX`**, 200 citations). Rows are inserted independently and de-duped on the unique key `(newsletterId, dataSourceId, sectionKey)`; citations whose `dataSourceId` is unknown are skipped. Response: **`{ recordedCount }`**.

From agents, use SDK namespace **`contentGenerationCitations`**: **`create`** for POST. The content-generation agent posts these best-effort after the newsletter persists; a recording failure never fails the newsletter.

```ts
const { updatedCount } =
  await dataApiClient.contentGenerationFetchedContent.create([
    { dataSourceId, content: fetchedBody, fetchProvider: "serper" },
  ]);
```

### Data collection existing URLs (`POST /api/v1/data-collection-existing-urls`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/data-collection-existing-urls.ts`. Zod schemas and the **`DATA_COLLECTION_EXISTING_URLS_MAX`** constant (500) live in `@workspace/agent-data-api-contract` (`data-collection.ts`); the manifest resource key is **`dataCollectionExistingUrls`**, so the same route exists under **`/api/v2/data-collection-existing-urls`** when callers pin `version: "v2"` on the SDK.

- **POST** — Body (`postDataCollectionExistingUrlsBodySchema`): **`tickerId`** (required, non-empty string), **`urls`** (required array of URL strings, each valid URL, at most **`DATA_COLLECTION_EXISTING_URLS_MAX`** entries per request). Response (`postDataCollectionExistingUrlsResponseSchema`): **`existingUrls`** — deduplicated list of strings from **`urls`** that already have at least one `data_source` row for that **`tickerId`** (exact match on the stored `url` column; no normalization); **`hostCounts`** — map of hostname → count of all `data_source` rows for that ticker (full corpus aggregation, used for pre-fetch host-fatigue ranking).
- **Empty list** — If **`urls`** is `[]`, the handler returns **`200`** with **`{ "existingUrls": [], "hostCounts": { … } }`** and still loads **`hostCounts`** from Prisma (no URL `IN` filter).
- **Errors** — **`401`** without a valid bearer JWT (same as other versioned routes). Invalid JSON body or Zod validation failures return **`400`** with `message: "Bad Request"` and **`errors`** (via shared `internalError` handling), consistent with other POST handlers.

From agents, use the SDK namespace **`dataCollectionExistingUrls`**: **`create`** for POST. The data-collection agent dedupes candidate URLs, then chunks requests so each POST stays within **`DATA_COLLECTION_EXISTING_URLS_MAX`**.

```ts
const { existingUrls, hostCounts } =
  await dataApiClient.dataCollectionExistingUrls.create({
    tickerId,
    urls: ["https://news.example/a", "https://news.example/b"],
  });
// existingUrls is a subset of urls that already exist in data_source for this ticker
// hostCounts maps hostname → total sources for the ticker (for fetch ranking)
```

### Data collection dead URLs (`POST /api/v1/data-collection/dead-urls/lookup`, `POST /api/v1/data-collection/dead-urls/record`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/data-collection-dead-url.ts`. Schemas and TTL helpers live in `@workspace/agent-data-api-contract` (`data-collection-dead-url.ts`). Manifest keys are **`dataCollectionDeadUrlsLookup`** and **`dataCollectionDeadUrlsRecord`** (custom path segments under `/data-collection/dead-urls/…`).

- **POST lookup** — Body: **`tickerId`**, **`urls`** (at most **`DATA_COLLECTION_DEAD_URLS_LOOKUP_MAX`**, 500). Response: **`deadUrls`** — subset of **`urls`** that are still cached in the `dead_url` table for that ticker with **`expiresAt > now()`**.
- **POST record** — Body: array of **`{ tickerId, url, errorCategory, httpStatus? }`**. Only terminal categories are stored (`provider_http_error` with status 404/403/410/451, `provider_data_invalid`, `content_too_short`). The service computes TTL (`expiresAt`) and upserts by URL (refreshing expiry on repeat failures). Response: **`{ message, recordedCount }`**.

From agents, use SDK namespaces **`dataCollectionDeadUrlsLookup`** and **`dataCollectionDeadUrlsRecord`**: **`create`** for POST. The data-collection agent looks up dead URLs after existing-URL dedupe and records cacheable failures after each fetch round (best-effort; lookup/record failures do not abort the run).

```ts
const { deadUrls } = await dataApiClient.dataCollectionDeadUrlsLookup.create({
  tickerId,
  urls: candidateUrls,
});

await dataApiClient.dataCollectionDeadUrlsRecord.create([
  {
    tickerId,
    url: "https://news.example/missing",
    errorCategory: "provider_http_error",
    httpStatus: 404,
  },
]);
```

### Publisher authority (`POST /api/v1/publisher-authority/stale`, `POST /api/v1/publisher-authority`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/publisher-authority.ts`. Schemas live in `@workspace/agent-data-api-contract` (`publisher-authority.ts`). Manifest keys are **`publisherAuthorityStale`** and **`publisherAuthority`**.

Publisher authority is a cached OpenPageRank score per registrable domain, used only to break ties between articles of equal section fit. It never decides whether an article is included.

- **POST stale** — Body: **`domains`** (at most **`PUBLISHER_AUTHORITY_LOOKUP_MAX`**, 500) and **`ttlDays`** (default **`PUBLISHER_AUTHORITY_DEFAULT_TTL_DAYS`**, 30). Response: **`domains`** — the subset with no `domain_authority` row, or whose **`refreshedAt`** is older than the TTL. A domain the provider could not score still has a row, so it is not re-submitted every run.
- **POST record** — Body: array of **`{ domain, openPageRank, globalRank, referringDomains, asOf }`**, all nullable except **`domain`**. Upserts by domain and stamps **`refreshedAt`**. Response: **`{ message, recordedCount }`**.

Both collection agents call these at the end of a run, for the domains of articles they actually persisted. The refresh helper lives in `@workspace/agent-ingestion` (`refreshPublisherAuthority`), and a blank **`publisher_authority.apiKey`** in the Hermes agent config disables enrichment without affecting the run.

```ts
const { domains } = await dataApiClient.publisherAuthorityStale.create({
  domains: persistedDomains,
  ttlDays: 30,
});

await dataApiClient.publisherAuthority.create([
  {
    domain: "detik.com",
    openPageRank: 8.03,
    globalRank: 10915,
    referringDomains: 3738,
    asOf: "2026-07-01",
  },
]);
```

### Content generation newsletters latest (`/api/v1/content-generation-newsletters-latest`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/content-generation.ts`. Schemas live in `@workspace/agent-data-api-contract` (`content-generation.ts`).

Used by the content-generation agent for the **skip-if-fresh** precheck (MP-CGA-006).

- **GET** — Query (`getContentGenerationNewslettersLatestQuerySchema`):
  - `tickerId` (required).
  - `windowStart` — required ISO 8601 datetime (inclusive).
  - `windowEnd` — required ISO 8601 datetime (exclusive).
- **GET response** — `getContentGenerationNewslettersLatestResponseSchema`:
  - `hasNewsletter` (boolean) — true if at least one newsletter matching the ticker exists within `[windowStart, windowEnd)`.
  - `newsletterId` (string | null) — ID of the most recent qualifying newsletter, or `null`.
  - `newsletterCreatedAt` (ISO 8601 datetime | null) — when that newsletter was written, or `null`.
  - `analyzedSinceCount` (integer) — sections classified for the ticker after `newsletterCreatedAt`. Non-zero means skipping the run would discard analysis the existing newsletter never saw, which the agent records as `skipped_fresh_newsletter_stale_analysis` rather than `skipped_fresh_newsletter_exists`. Always `0` when no newsletter exists in the window.

From agents, use the SDK namespace **`contentGenerationNewslettersLatest`**: `get` for the query object.

### Analysis (`/api/v1/analysis`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/analysis.ts`. Schemas live in `@workspace/agent-data-api-contract` (`analysis.ts`).

**Engineering note (MP-ART-ANALYSIS-002):** Eligibility time windows are applied **on the server** via optional GET query params. That differs from **`GET /api/v1/data-collection`**, which only applies a `createdAt` range when **both** `start` and `end` are present; analysis GET applies `gte` / `lte` **independently** when each param is set (same pattern as delivery-run listing). Omitting both preserves the previous unbounded (by time) behavior.

- **GET** — Query (`getAnalysisQuerySchema`):
  - `tickerId` (required).
  - `unanalyzed` — optional (`"true"` | `"false"` strings). When omitted, defaults to `"true"` (incremental backlog: sources with no `article_relevance` row for that ticker). `"false"` returns all `DataSource` rows for the ticker for re-scoring workflows (FR2).
  - `start` — optional ISO 8601 datetime; when set, only sources with `createdAt >= start` (inclusive), FR1.
  - `end` — optional ISO 8601 datetime; when set, only sources with `createdAt <= end` (inclusive), FR1. If both `start` and `end` are set, `start` must not be after `end` (validation error).
  - `limit` — optional positive integer, **at most** **`ANALYSIS_GET_DATA_SOURCE_LIMIT_MAX`** (currently **10**, see `@workspace/agent-data-api-contract`). Article-analysis sets `limit` from Hermes config via `min(maxBatchSize, analysisGetDataSourceLimitMax)` (defaults match that cap). When set, `dataSources` returns at most `limit` rows (ordered by `createdAt` ascending) while **`dataSourceTotalCount`** still reflects the full filtered count.
- **GET response** — Includes `dataSources`, **`dataSourceTotalCount`**, vocabulary, `existingEntities`, `relevanceSelectionState` (**`utcDayStartIso`**, **`selectedCountToday`**), and **`lastRelevanceScoredAtIso`**: ISO 8601 of the latest `article_relevance.scored_at` for the ticker, or `null` if none (used by article-analysis debounce). Each `dataSources` row also carries **`ticker`** — per-article issuer context (`symbol`, `name`, `sector`, `industry`, `subIndustry`, `businessActivity`) for section classification, or **`null`** for ticker-agnostic rows.
- **POST** — Body validated by `postAnalysisBodySchema`: `tickerId`, optional arrays `entities`, `relations`, `articleEntities`, `articleRelevances`. Response includes aggregate counts (`entitiesCreated`, `entitiesReused`, `relationsCreated`, `articlesScored`, `articlesSelected`).

From agents, use the SDK namespace **`analysis`**: `get` for the query object (including optional `limit` and `timeWindow` as `start` / `end`), **`create`** for POST.

### Analysis data-source delete (`POST /api/v1/analysis-data-source-delete`)

Used by the article-analysis agent to remove unrecoverable sources (for example repeated extraction parse failures) without direct DB access from the agent process.

- **POST** — Body (`postAnalysisDataSourceDeleteBodySchema`): `tickerId` (required) and `dataSourceId` (UUID, required).
- **POST response** — `{ deleted: boolean }` where `deleted=true` only when a row matching both `tickerId` and `dataSourceId` existed and was removed.

From agents, use SDK namespace **`analysisDataSourceDelete`** with `create`.

### Delivery run (`/api/v1/delivery-run`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/delivery-run.ts`. Contract types and Zod schemas live in `@workspace/agent-data-api-contract` (`delivery-run.ts`).

- **GET** — Lists persisted runs. **Query** (all optional, validated by `deliveryRunQuerySchema`):
  - `tickerId` — UUID, filter by ticker.
  - `outcome` — One of `success`, `skipped`, `failed`, `partial_success`, `skipped_all_already_delivered`.
  - `start` — ISO 8601 datetime; when set, only rows with `createdAt >= start` (inclusive).
  - `end` — ISO 8601 datetime; when set, only rows with `createdAt <= end` (inclusive).
- **POST** — Inserts one run and nested recipient rows (`postDeliveryRunBodySchema`). Body includes run id, agent id/version, ticker id, optional `newsletterId`, `outcome`, optional `stage`, counts, `durationMs`, optional Hermes correlation fields (`jobId`, `hermesExecutionId`, `hermesScheduleId`, `pipelineStepId`, `scheduleExecutionId`), optional `runSkipReason` / `recipientErrorSummary` / `resendMessageIds`, and a `recipients` array (per-`userTickerId` status, attempts, optional Resend/error fields). **`createdAt` is not accepted in the body**; the API sets it at insert time.

From agents, use the SDK namespace **`deliveryRun`**: `get` for the query object, **`create`** for POST (manifest maps POST to `create`).

```ts
await dataApiClient.deliveryRun.get({
  tickerId,
  outcome: "success",
});

await dataApiClient.deliveryRun.create({
  id: runId,
  agentId: "delivery",
  agentVersion: "1.0.0",
  tickerId,
  outcome: "success",
  successCount: 1,
  failureCount: 0,
  skippedCount: 0,
  durationMs: 1200,
  recipients: [],
});
```

`createdAt` on the stored row is set by the **server** when the POST is handled (callers must not supply it in the body).

For example, in agents:

```ts
const dataApiClient = createAgentDataApiClient({
  baseUrl: env.AGENT_DATA_API_URL,
```

### Content generation run (`/api/v1/content-generation-runs`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/content-generation-run.ts`. Contract types and Zod schemas live in `@workspace/agent-data-api-contract` (`content-generation-run.ts`).

- **GET** — Lists persisted runs. **Query** (all optional, validated by `contentGenerationRunQuerySchema`):
  - `cursor` — `id` of the last item from the previous page.
  - `limit` — Page size, between 1 and 100. Default 50.
  - `tickerId` — non-empty string ticker id, filter by ticker.
  - `outcome` — One of `success`, `skipped`, `failed`.
  - `startTime` — ISO 8601 datetime; when set, only rows with `createdAt >= startTime` (inclusive).

```ts
const run = await dataApiClient.contentGenerationRuns.create({
```

### Delivery agent (Hermes config + semantics)

- **Config (`configSchema`):** required **`resendApiKey`** and **`resend.from`** (no env fallback); optional `resend.replyTo` / **`resend.tags`**, **`send.includeHtml` / `send.includeText`** (defaults `true`; at least one required), `rateLimit.minIntervalMs` + `maxSendsPerMinute`, `retry` (`maxAttempts`, `baseDelayMs`, `maxDelayMs`, `jitter`), `template.newsletterVariant` (`default` only in v1), optional **`template.preferencesUrl`** (absolute URL; when set, the default newsletter template shows a “Manage preferences” link).

### Article analysis run record (`/api/v1/article-analysis-run`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/article-analysis-run.ts`. Schemas live in `@workspace/agent-data-api-contract` (`article-analysis-run.ts`).

Article-analysis writes this row twice per run: once to claim it before the first classification, and once on completion. The POST is an upsert on `id`, so both writes address the same row.

- **POST body** — `postArticleAnalysisRunBodySchema`:
  - `status` — `running` while in flight, then `success`, `partial_success`, or `failed`.
  - `completedAt` — omitted on the claim write, set on the completion write. `SELECT ... WHERE completed_at IS NULL` is therefore the liveness query.
  - `stalledBefore` (optional ISO 8601 datetime) — marks every other run still `running` that started before this instant as `failed` with stop reason `stalled`, before this run's row is written. A `running` row older than the agent's timeout is a crashed run, which the schema cannot otherwise distinguish from a live one. Article-analysis sends it only on the claim write, using a one-hour threshold.
- **POST response** — `postArticleAnalysisRunResponseSchema`: `message`, plus `stalledCount` when `stalledBefore` swept any rows.

### Newsletter feedback (`POST /api/v1/newsletter-feedback-record`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/newsletter-feedback.ts` and `services/newsletter-feedback.ts`. Schemas live in `@workspace/agent-data-api-contract` (`newsletter-feedback.ts`). Consumed by the [newsletter-feedback agent](/mediapulse/apps/agents/newsletter-feedback).

- **Body:** `graphMessageId`, `senderEmail`, `subject?`, `rawBody`, `receivedAt`, `inReplyToMessageId?`, `sentiment` (`positive | negative | neutral | mixed`), `category` (`praise | complaint | feature_request | bug | question | other`), `classifierModel?`.
- **Behavior:** Idempotent on `graphMessageId` (`created: false` on replay). Correlates the reply to a subscriber/newsletter by parsing the self-describing newsletter Message-ID out of `inReplyToMessageId`, falling back to a `senderEmail` match against `mediapulse_user`. The raw body is always stored, even when correlation is empty.
- **Response:** `feedbackId`, `created`, and `correlated` (`{ userId?, userTickerId?, newsletterId? }`).

### Ticker relevance terms (`GET /api/v1/ticker-relevance-terms`)

Implemented in `apps/mediapulse/agent-data-api/src/routes/ticker-relevance-terms.ts` and `services/ticker-relevance-terms.ts`. Schemas live in `@workspace/agent-data-api-contract` (`ticker-relevance-terms.ts`). The manifest key is **`tickerRelevanceTerms`**.

- **GET** — No query parameters. Returns **`{ tickers }`**, one entry per **active** ticker as **`{ id, symbol, terms }`**. A ticker counts as active when it has an active `SearchQuerySet` (`search_query_set.is_active = true`); the `ticker` table has no `isActive` column.
- **`terms`** is the deduplicated, trimmed, non-empty union of the ticker's `symbol`, `name`, every alias, each peer's `symbol` and `name`, and the `sector`, `industry`, `subSector`, and `subIndustry` labels. Deduplication is case-insensitive and keeps the first-seen casing. `businessActivity` is deliberately excluded because it is long prose rather than a matchable term.
- Peers reuse the sector/industry resolution from `services/query-analysis-context-helpers.ts` and stay capped at `QUERY_ANALYSIS_PEER_LIMIT` per ticker. Candidates for every active ticker load in one batched query rather than one query per ticker.

From agents, use the SDK namespace **`tickerRelevanceTerms`**.

```ts
const { tickers } = await dataApiClient.tickerRelevanceTerms.get({});

for (const ticker of tickers) {
  // ticker.terms is ready for substring or token relevance matching
}
```

### Knowledge ingestion (`/api/v1/knowledge/*`)

Storage for the Storyline knowledge base, read and written by the `knowledge-ingestion` agent.

- `GET /api/v1/knowledge/candidate-sources` — Data Sources to consider, oldest first, with a `watermark` for the next run. With no `since`, the batch resumes from the newest watermark left by a run that finished successfully, so a scheduled agent advances through the corpus instead of rewalking its start. Failed runs are ignored, otherwise the articles a half-finished batch never reached would be skipped for good. `fromStart=true` ignores the watermark for a deliberate rebuild, and `resumedFrom` reports where the batch actually began. Returns the whole collected corpus rather than only articles a Section admitted, because a thread grouped from admitted articles alone would depend on the classification it exists to inform. `text` prefers fetched `content` and falls back to the collection `description`.
- `POST /api/v1/knowledge/storyline-candidates` — Storylines sharing at least one anchor with the candidate. Retrieval is by anchor, never by Ticker: Storylines are global, so narrowing by the candidate's own tickers would hide a thread opened under another issuer and fork it. Storylines flagged `format` are excluded.
- `POST /api/v1/knowledge/storylines` — opens a Storyline and its first Development.
- `POST /api/v1/knowledge/developments` — records the next move on an existing Storyline, storing the attach evidence.
- `POST /api/v1/knowledge/development-citations` — adds one more reporting Data Source to a move already recorded.
- `POST /api/v1/knowledge/ingestion-runs` and `POST /api/v1/knowledge/ingestion-runs/finish` — the run chronicle.

A Data Source cites at most one Development, enforced by a unique constraint, because an article reports exactly one move. Candidate sources therefore exclude anything already cited, and every write returns the existing Development instead of creating a second one. Re-ingesting an article is a no-op rather than a duplicate move, so a watermark that fails to advance costs a wasted run and nothing else.

Every write returns `{ storylineId, developmentId, locked, lockedReason }`. The ceiling (`KNOWLEDGE_MAX_TICKERS`, `KNOWLEDGE_MAX_DEVELOPMENTS`) is applied server-side on each write and the agent only counts the outcome, so the two cannot drift. A locked Storyline accepts no further automatic attachment until an operator rules on it, which is what stops one thread chaining across unrelated stories.

## Endpoint change workflow

When the API surface changes (new endpoint, removed endpoint, or request/response changes), follow this sequence to keep contract, server routes, SDK, and agents in sync:

1. **Contract first:** update schemas and exported types in `@workspace/agent-data-api-contract`.
2. **Manifest update:** add or update the resource in `agentDataApiManifest` (this is the canonical source of route shape).
3. **API wiring:** implement/update handlers in `apps/mediapulse/agent-data-api/src/routes` and `src/services`, then wire them in the typed handler map used by route registration.
4. **SDK alignment:** update `@workspace/agent-data-api-client` if request/response types changed.
5. **Consumer updates:** update agent callsites that use the SDK.
6. **Validation:** update tests, then run `pnpm code-quality`.

See `.cursor/skills/agent-data-api-endpoints/SKILL.md` for the detailed checklist.
