## Purpose

User Registration is a Next.js app that provides a user-facing registration and onboarding interface. It shares the same stack as Hermes (Next.js, `@workspace/env`, `@workspace/ui`) but is a distinct deployable app.

When you implement real signups, create **`MediapulseUser`** rows (and `user_ticker` as needed) in the Mediapulse database. Do **not** create Hermes orchestration **`User`** rows for end subscribers; those are **admin** accounts only.

## Key routes / entrypoints

- Home: `/` — landing page for user registration flow.
- `POST /api/confirm/request` — sends a pending confirmation email for the **Other** signup path (rate-limited; always returns `{ ok: true }` on valid input).
- `GET /api/confirm?token=…` — browser confirmation link from outbound email; confirms the subscription and sends the welcome email.

## Signup UX

After the user fills in name, language, and ticker and clicks **Subscribe**, a modal offers platform-aware mail-app choices:

- **Microsoft Outlook** — opens an `ms-outlook://` compose draft on mobile and Windows (Outlook must be installed; iOS uses `ms-outlook://emails/new`). On macOS desktop, Outlook does not register that scheme, so the app uses `mailto:` instead (Outlook opens when it is the default mail handler).
- **Apple Mail / Windows Mail / Default mail app** — opens the existing `mailto:` draft flow.
- **Other** — second modal collects the user's email address; MediaPulse sends a confirmation link via Resend.

Both paths converge on the same `user_ticker` rows in the Mediapulse database.

After choosing Outlook or another mail app, the **Almost done** screen explains that if the mail app did not open, the user can enter their email address and MediaPulse will send a confirmation link instead.

## Ingesting Registrations (Agent)

Signups are processed asynchronously through a dedicated Hermes-scheduled backend agent, `user-registration`.
Because MediaPulse supports login-less registration over email, the flow works like this:

1. The `@mediapulse/user-registration` home page loads the ticker list from **agent-data-api** (`GET /api/v1/user-registration-tickers`, no bearer token—same as the unsubscribe and web-signup routes) so choices stay aligned with the Mediapulse `ticker` table.
2. For the mail-app path, the front-end opens a mail draft (`mailto:` or Outlook compose) for the user to send from their own address.
3. For the **Other** path, the app calls `POST /api/confirm/request`, which registers an unconfirmed row via `POST /api/v1/user-registration-web-signup` and emails a signed link to `GET /api/confirm`.
4. The `user-registration` agent reads a shared Microsoft Outlook inbox via `@mediapulse/outlook-inbox` for mail-app signups.
5. The agent parses the desired ticker. Waitlist / Unknown tickers trigger an outbound email.
6. On successful registration for a known ticker, the agent sends a Resend confirmation email plus `user-registration-confirm` for mail-app signups; the web path confirms via the link and sends the same welcome email from the Next.js app.

### Day-1 newsletter

When a subscription becomes active (confirmed and enabled for the first time, or re-enabled after an unsubscribe), **agent-data-api** asks Hermes for a same-day issue instead of leaving the subscriber to wait for the next morning run. Both signup paths go through the same service functions, so both trigger it.

The decision is made per ticker, under a Postgres advisory lock so two confirmations for the same ticker can't race:

| Ticker state | What runs |
| --- | --- |
| Latest issue at most `MEDIAPULSE_DAY1_LATEST_ISSUE_MAX_AGE_HOURS` old (36 by default), in the subscriber's language | **Day 1 Latest Issue**: delivery only. Checkpoints keep existing subscribers from getting it twice. |
| Latest issue fresh, but not translated into the subscriber's language | Nothing. The next nightly run covers it. |
| No issue yet, or a stale issue and no other active subscribers | **Day 1 Newsletter**: query-analysis, data-collection, article-analysis, content-generation and delivery for that ticker. |
| Stale issue while other subscribers are active | Nothing. A mid-day issue would reach the existing subscribers too, so the nightly run keeps the ticker. |
| A Day 1 Newsletter run already started for the ticker within `MEDIAPULSE_DAY1_BOOTSTRAP_DEDUPE_MINUTES` (120) | Nothing. That run's delivery step picks the new subscriber up. |
| The same subscription already dispatched within that window (a repeated or concurrent confirmation) | Nothing. |

Every decision is stored in `day1_newsletter_dispatch` with its kind, status (`dispatching`, `fired`, `failed`, `skipped`), skip reason, Hermes execution id or error, and is shown on the Hermes **Day 1 Dispatches** page. The event call is fire-and-forget with a `MEDIAPULSE_DAY1_TRIGGER_TIMEOUT_MS` timeout and is never retried, and a failure never affects registration.

Which pipelines run is configured in Hermes, not in Mediapulse. agent-data-api sends Hermes the `day1.full-chain` or `day1.latest-issue` event with the ticker as the `tickerId` run parameter, using `HERMES_API_URL` and `DOMAIN_INTEGRATION_API_KEY`. In Hermes, an HTTP trigger started by that event runs the chosen pipeline. Until one exists, dispatches are recorded as skipped with "No Hermes trigger listens for this day-1 event yet", and disabling the trigger switches day-1 off. [Hermes setup](/mediapulse/hermes-setup#day-1-pipelines) lists the MCP calls that create both pipelines and event triggers. A thin ticker may still produce no issue on day 1: content-generation needs at least two articles across two sections.

### Inbox hygiene (archiving + retries)

- **Archive on completion**: When a message is fully handled (including unparseable/invalid cases), the agent archives it to keep the inbox clear.
- **Confirm is best-effort**: If the confirm API fails after registration, the agent still archives the message (confirmation is retried implicitly on subsequent runs via idempotent register/confirm behavior).
- **Bounded retry for register**: The agent retries the register API once on transient failures (429/5xx or network errors). If it still fails, the message is left in the inbox so the next scheduled run can retry.

### Message lifecycle (how a message leaves the queue)

The agent reads **unread** messages and a message must actually leave that unread set once handled, or oldest-first ordering will keep re-fetching it and never reach newer signups.

- **Folder-scoped fetch**: The list query is scoped to a single folder (`mailFolder`, default `inbox`) via `/mailFolders/{folder}/messages`, not the whole mailbox. Moving a handled message to Archive therefore removes it from the result set. Set `mailFolder: ""` to query the whole mailbox.
- **Mark read, then move**: Archiving marks the message read (`PATCH isRead: true`) and then moves it to Archive. Read is set first so that even if the move fails, the message no longer matches the `isRead eq false` filter and is not reprocessed. A re-listed same-id message is harmless anyway because register is idempotent.
- **Oldest-first, batched**: Messages are processed oldest-first so the backlog drains in arrival order. `maxMessagesPerRun` caps how many subscription emails are processed per run and is floored (minimum 10) because a value like 1 lets a single slow or failing message block all progress.
- **Dead-letter guard**: A message that throws on every run is archived (marked read and moved) after `maxMessageAttempts` consecutive failures (default 5) so a poison message cannot hold the oldest slot forever. Rate-limited messages are not counted toward this and are simply retried on a later run.
- **Coverage signal**: `details.inboxScan` reports `{ pagesScanned, messagesScanned, matchedMessages, limit, drained, mailFolder, refetchedTerminal }`. `drained: false` means signups remain beyond this run's `limit` (expected when volume exceeds `maxMessagesPerRun`, converging over runs). `refetchedTerminal > 0` is a regression alarm: it means already-read mail is leaking back into the unread queue.
