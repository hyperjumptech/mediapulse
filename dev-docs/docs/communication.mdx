This page explains **how the different parts of the system talk to each other**: who calls whom, with which credentials, and how verification works. For a high-level picture of components, see [Architecture](/architecture). For environment variables and production setup, see [Production](/production).

## Two kinds of auth

The system uses **two separate auth mechanisms**:

| Purpose                                   | Credential               | Who uses it           | How it’s verified                                                     |
| ----------------------------------------- | ------------------------ | --------------------- | --------------------------------------------------------------------- |
| **Invocation** (calling an agent)         | Short-lived **JWT**      | Hermes, hermes-worker | Agent calls `POST /api/verify` (JWT-only)                             |
| **Service calls** (agent → platform APIs) | Admin-issued **API key** | Agents                | agent-data-api and agent-registry-api call `POST /api/verify-api-key` |

Invocation auth proves “the scheduler is allowed to run this agent.” Service auth proves “this agent is allowed to read/write data or register itself.”

---

## Invocation flow: Hermes or hermes-worker → Agent

When a pipeline runs (from the dashboard or on a schedule), the caller **never** sends the raw scheduler API key to agents. It first gets a short-lived JWT from agent-auth-api, then sends that JWT to the agent.

**Where the scheduler key comes from:** An **admin** must create a long-lived API key in the **Hermes dashboard** (e.g. **API keys** in the sidebar). When creating the key, set **purpose** to `scheduler`. The raw key is shown once at creation; that value is what you set as `AGENT_API_KEY` in the environment for Hermes and hermes-worker. Hermes and hermes-worker use this key only to call `POST /api/token`; they never send it to agents.

**Steps:**

1. **Hermes** (manual run) or **hermes-worker** (scheduled run) is configured with a long-lived **scheduler API key**. This key must be **created by an admin in the Hermes dashboard** (API keys → Create, purpose `scheduler`). The admin copies the key once at creation and sets it as `AGENT_API_KEY` in the env for Hermes and hermes-worker. The caller then uses it to call **agent-auth-api** `POST /api/token` with `Authorization: Bearer <scheduler_key>`.
2. **agent-auth-api** checks the key in the DB (active, purpose `scheduler`), signs a JWT with `AGENT_AUTH_JWT_SECRET`, and returns `{ token, expiresIn }` (e.g. 15 minutes).
3. Hermes/hermes-worker **caches** the JWT and uses it for all agent requests until close to expiry, then fetches a new one.
4. For each pipeline step, the caller sends `POST` to the agent URL with `Authorization: Bearer <jwt>` and the step input/config.
5. The **agent** (via `@workspace/agent-runtime` bearer middleware) receives the request, extracts the Bearer token, and calls **agent-auth-api** `POST /api/verify` with that token.
6. **agent-auth-api** `POST /api/verify` is **JWT-only**: it verifies signature and expiry. If the token is not a JWT or is invalid, it returns 401. The agent rejects the request unless it gets 200.
7. The agent runs its logic and returns the result.

**Important:** The scheduler API key is only ever sent to agent-auth-api. Agents only ever see the JWT, so a leaked JWT expires in minutes and the key can be revoked in the dashboard without sending it to every agent.

## Service-call flow: Agent → agent-data-api / agent-registry-api

Agents need to call **agent-data-api** (read/write pipeline data) and optionally **agent-registry-api** (self-register). For these calls, agents use an **admin-issued API key** (not the JWT they received for invocation). That key is configured in the agent’s environment (e.g. from the dashboard, purpose `general` or similar).

<Mermaid
  chart={`sequenceDiagram
  participant Agent as Agent
  participant DataAPI as "agent-data-api"
  participant RegistryAPI as "agent-registry-api"
  participant AuthAPI as "agent-auth-api"

Agent->>DataAPI: GET/POST /api/... with Bearer api_key
DataAPI->>AuthAPI: POST /api/verify-api-key with Bearer api_key
AuthAPI->>AuthAPI: Look up hashed key in DB
AuthAPI->>DataAPI: 200 valid true
DataAPI->>Agent: 200 + data

Agent->>RegistryAPI: POST /api/agents/register with Bearer api_key
RegistryAPI->>AuthAPI: POST /api/verify-api-key with Bearer api_key
AuthAPI->>RegistryAPI: 200 valid true
RegistryAPI->>Agent: 200 registered
`}
/>

**Steps:**

1. The **agent** holds an **API key** in its env (e.g. `AGENT_REGISTRY_API_KEY` for registry; for data API the agent runtime uses the same key when calling `dataApiGet` / `dataApiPost`). It sends `Authorization: Bearer <api_key>` to agent-data-api or agent-registry-api.
2. **agent-data-api** and **agent-registry-api** do **not** validate the key themselves. They call **agent-auth-api** `POST /api/verify-api-key` with the same Bearer value.
3. **agent-auth-api** hashes the key, looks it up in the API key table (active keys only), and returns 200 with `{ valid: true }` or 401.
4. The data/registry API allows or denies the request based on that result.

This keeps **all API key storage and verification in one place** (agent-auth-api + DB). agent-data-api and agent-registry-api stay stateless for auth.

## Where to configure what

| Component          | Needs                                   | Used for                                                                                                                                                            |
| ------------------ | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **agent-auth-api** | `AGENT_AUTH_JWT_SECRET`                 | Signing/verifying JWTs (`/api/token`, `/api/verify`). Required for JWT flow.                                                                                        |
| **Hermes**         | `AGENT_AUTH_API_URL`, `AGENT_API_KEY`   | Minting JWT when user runs a pipeline from the dashboard. `AGENT_API_KEY` = scheduler key **created by admin in Hermes dashboard** (API keys, purpose `scheduler`). |
| **hermes-worker**  | `AGENT_AUTH_API_URL`, `AGENT_API_KEY`   | Minting JWT for scheduled pipeline runs. Same scheduler key as Hermes; **create it in the Hermes dashboard** (API keys, purpose `scheduler`).                       |
| **Agent**          | `AGENT_AUTH_API_URL`                    | Verifying invocation JWT via `POST /api/verify`.                                                                                                                    |
| **Agent**          | API key (e.g. in env or from dashboard) | Calling agent-data-api and agent-registry-api; those services verify via `POST /api/verify-api-key`.                                                                |

For a full list of env vars per app, see [Production](/production).
